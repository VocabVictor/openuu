# 2026-09-13 的判断失误与验证手段

今天有几次，某个会话先给出一个结论，随后自己或别人把它推翻了。这份文档不是检讨，
是把"哪一类结论容易错、它对应的验证手段是什么"记下来，给接手的人省一轮弯路。

每条的格式一致：**当时的结论 → 它错在哪 → 什么让人发现不对 → 用什么手段定的案**。

收录的判据只有一条（52 提出）：**心得要求下一个人有同样的品味，信号只要求他看得见。**
一条经验站不站得住，看它有没有给出**别人也能看见的东西**——"基线数字本身是个探测器"
落在 222 这个数上，"两个用法共用一个名字"落在"争论本身还在"上，"写没写成功"落在文件数上，
"截图是不是真的花屏"落在同一帧里开始菜单那块像素上。反过来，**凡是读起来像格言、
却说不出该去看什么的，都是还没写完**，不是写得不好。往这份文档里加东西之前先问一句：
**读者该去看什么？** 答不上来就先别加。

还有一条判据是关于**要不要单开一条**的（51 提出）：
**一条经验值得单列，当且仅当它改变一个动作。**
只添理由、不添动作的，归进它所支持的那一条——让那一条的理由变厚，
而不是让目录变长。第 44 条该单列，因为它把动作从"比数量"换成了"按身份对账"；
而"报失误报得具体，别人才能接着往上推一层"不单列，
因为知道了它之后要做的事，和第 19 条已经要求的一模一样。

第三条是关于**写的人**的：**一条教别人去看证据的条目，作者自己得先看过。**
否则它就是一次传闻的转述，形状和它自己的要求不一致。
第 45 条正文让读者用三个命令定案，所以那三个命令的读数是本会话在本机跑出来的，
不是从别人的消息里抄的——其中"生成文件里那个符号出现 0 次"这一条，
消息里本来没有，是跑了才有的。

## 1. 路径推演压过了工具事实

**结论**：一个子代理报告，今天的拆分在 `flutter/lib/common/` 下留了 14 个
`import '../../consts.dart'`，加上另外两处，共 16 个无法解析的 import，移动端因此编译不了。
推演看着无懈可击：`flutter/lib/common/` 上溯两级是 `flutter/`，而 `flutter/consts.dart`
确实不存在，本机 `ls` 与编译机 `Test-Path` 都确认。

**错在哪**：那 16 处能正常解析。lib 下的文件按 `package:flutter_hbb/…` 解析，
超出包根的多余 `..` 被 URI 规范化吸收，最终落到 `package:flutter_hbb/consts.dart`，
也就是 `flutter/lib/consts.dart`。

**什么让人发现不对**：它与另一个事实直接冲突——今天每一轮 `flutter analyze` 都是 0 error。
一个能让整个移动端编译不了的问题，不可能不被分析器报出来。**两个事实互相矛盾时，
至少有一个是错的，不能挑顺手的那个信。**

**怎么定的案**：做一次能证伪的实验。把 `branding.dart:9` 改成一个确定不存在的
`'../../zzz_nonexistent.dart'`，推上编译机分析——立刻报
`error - Target of URI doesn't exist … uri_does_not_exist`，还连带两条
`undefined_identifier`；换回原样则干净。这同时证明了两件事：分析器确实覆盖该文件，
以及原来的写法确实能解析。

**可复用的手段**：当推理与工具结论冲突，构造一个"如果我的推理成立，它必然报错"的输入，
看工具认不认。不要再读一遍代码，也不要把推理讲得更细。

## 2. 只读一个函数就给一个功能定性

**结论**：移动端的扫码导入还停在旧的 `config=` 格式，没接上今天的新 provisioning。
依据是 `mobile/pages/scan_page.dart` 的 `showServerSettingFromQr` 只认 `config=` 前缀。

**错在哪**：完全接上了。当天另一个会话新增了 `flutter/lib/common/config_import.dart`：
`isConfigPayload` 同时认 `openuu://config/…` 与 legacy `config=`，`confirmImportConfig`
先调 `bind.mainPreviewConfigText` 出预览、确认后调 `bind.mainImportConfigText`，
与桌面 provisioning 走同一对 FFI。我读到的那个函数只是旧格式的回退分支。

**什么让人发现不对**：去数当天触及 `flutter/lib/mobile/` 的提交时，看见了
`feat(mobile): scan a configuration QR code, also on first start`。

**怎么定的案**：`git log --since="2026-09-13 00:00" -- <该目录>`，然后读那个提交的 diff。

**可复用的手段**：给一个功能下"没做/缺失"的定性之前，先看该区域当天的提交。
在多会话并行的一天里，"我读到的代码"和"当前的代码"之间可以隔着好几个提交。
顺带一个教训：一个 `if/else` 里读到 else 分支，不等于没有 if 分支。

## 3. 把文件的行数当成方法的行数

**结论**：`AGENTS.md` 的 Tracked exceptions 记 `settings_state.dart` 是
"单个 `_SettingsState.build` 约 770 行"，而该文件现在 1020 行，所以记录已过时、该更新。

**错在哪**：记录是准确的。`_SettingsState.build` 实际跨 221–991 行，**771 行**。
文件 1020 行里另外 249 行是该类的字段和其它方法。Tracked exception 记的本来就是
"这个文件超限的原因是那个超长方法"，两个数字度量的是不同的东西。

**什么让人发现不对**：准备去改 `AGENTS.md` 时，顺手量了一下那个方法到底多长。

**怎么定的案**：从方法首行起逐行累加大括号层级，层级归零处即方法末行。

**可复用的手段**：拿两个数字说"对不上"之前，先确认它们度量的是同一个东西。
尤其当一个数字来自 `wc -l`、另一个来自一句自然语言描述时。

## 4. 被观察到的字符串未必出自我们的代码

**结论**：用户截图里工具栏显示 `FPS N/A`，看起来是质量监视器坏了，于是开始查
Rust 侧的 fps 上报到 Dart 侧取值的整条链路。

**错在哪**：监视器没坏。实测打开后数据正常，其中 FPS 0 是正确的——那一刻远端桌面静止、
被控端 `captured=0`。

**什么让人发现不对**：`FPS N/A` 这个串在全仓库搜不到。`N/A` 只用于指纹显示；
质量监控无数据时的回退值当时是 `-`，现已统一为 `—`。

**怎么定的案**：grep 整个仓库确认该字符串不存在，于是定位到截图里那一行位于屏幕最右上角、
紧挨着一排别的图标，是另一个应用的悬浮条。

**可复用的手段**：从截图或用户描述出发排查时，**第一步是确认那段文字出自我们的代码**。
这一步比读数据链路便宜得多，而且能一次排除整个方向。

（这条的第一手材料来自负责该问题的会话；我在其中的角色是先自证了我的改动与之无关，
并给出了链路上的排查点，那些点最后没用上，但归纳出来仍然成立：首帧前短暂无数据是正常的、
多显示器时两侧 display index 可能错位、全显示器分支缺 key 时填 0 而非 null。）

## 5. 症状所在的位置，常常不是缺陷所在的位置

**结论**：审计"局部失败导致整体降级"时，报告 `EncodingUpdate::Check` 的分支体是空的
（`libs/scrap/src/common/codec/encoder_update.rs:23`）——它只拿已被清空的配置重算一遍、
不重新探测，所以硬编码在本进程内不会自愈。这被当成一个独立缺陷报了上去，并据此安排了
单独的修复提交。

**错在哪**：空分支本身不是缺陷。`Check` 的职责就是"用当前配置重算协商结果"，
它之所以恢复不了任何东西，是因为上游的 `HwCodecConfig::clear` 把配置毁了。
"恢复路径没恢复"被记在了恢复路径头上，而真正的缺陷在毁配置的那一端。

**什么让人发现不对**：动手修的时候。为另一条缺陷选了"不清配置、只记下失败的那个编码器"
之后，再去写 `Check` 那个提交，发现**没东西可修了**——配置完整时，重算本来就是对的。
第二个信号更早就出现过：原方案（给 `Check` 加重新探测）会引入一个新问题（编码器一有波动
就 spawn 探测进程）。**"修果的方案会引入新问题"本身就是在错的层面上修的味道。**

**怎么定的案**：读 `Check` 到底重算什么、读 `clear` 确认它清空整张表且不落盘、
读 `start_check_process` 的 `already_set` 加 `Once` 两道闸确认"重新探测"必须绕过它们；
然后做反事实——先修因，看果是否自行消失。没有依赖任何命令输出。

**可复用的手段**：当"恢复路径不恢复"时，先问是不是上游把可恢复的东西毁了。
检验方式是反事实：先修因，再看果是否不治而愈。如果"修果"的方案会引入新问题，
那通常说明修错了层面。

## 6. 把"日志里查不到"当成证据之前

**结论**：接受了一份评审里的说法——"静止桌面很容易掉进 GDI 全帧拷贝路径"，并据此改了判据。

**错在哪**：那条规则在第一帧成功后就永久解除（`try_gdi` 归零），所以"会话中途因静止掉 GDI"
根本不会发生。真实风险窄得多，只存在于会话开头。

**什么让人发现不对**：自己复核代码路径，不是别人质疑。

**怎么定的案**：在两台被控端的全部历史日志里 grep（151 个文件加 55 个文件），
`No image` 零命中。**关键的一步是同时核对了改动前的旧措辞也含 `No image`**——
否则"零命中"可能只是日志缺失或措辞变更造成的假象。这一步让"没查到"升级成了"有证据表明没发生"。
同一次 grep 还暴露出 `fall back to gdi` 其实天天发生，只是走另一条分支
（28 次全在会话开始 0.5 秒内），最后牵出一个真问题。

**可复用的手段**：把"日志里查不到"当证据之前，先证明"真发生了就一定会留痕"——
检查旧版本的措辞、日志级别、文件覆盖范围。做完这一步，零命中才从"没查到"变成"没发生"。

## 7. "看起来像故障"与"设计如此"

**结论**：MSI 安装日志里 `Failed to start service: OpenUUConfigImport, error: 0x41D`
（1053 超时）看着像一个缺陷，一度被当作待跟进项，并被推测为"导入耗时超过 SCM 的 30 秒窗口"。

**错在哪**：这是设计内的预期路径。`--import-config` 跑完就退出、从不向服务控制管理器报告状态，
所以启动请求必然失败；源码注释原文就是 "that is the expected outcome"。
与它成对出现的 `Failed to open service … 0x424`（1060）来自安装前清理陈旧临时服务那次调用，
首次安装当然找不到。

**什么让人发现不对**：去读了发出这两行日志的代码，而不是从日志措辞往回推。

**怎么定的案**：定位到 `res/msi/CustomActions/ServiceActions.cpp` 的
`TryImportConfigByTempService` 与 `ServiceUtils.cpp` 的 `MyStartServiceW`——后者对
`StartServiceW` 的任何失败都用同一句措辞，不区分预期与否。

**可复用的手段**：日志里的"失败"是写日志的人选的词，不是事实的性质。
判断一行日志是不是缺陷，要去看发出它的那几行代码。
真正该改的是措辞（已记入 backlog），而不是那个行为。

## 8. 一次成功的构建不等于一个能用的产物

今天真发生过一次：有人报"含某改动的包已构建完成"，而它根本没建完——后台任务的通知回来是
`status=killed`（本机内存不足被杀）。发现不对靠的是那条通知与刚说过的话直接冲突；
定案靠的是 ssh 上编译机对产物做判定：`libopenuu.dll` 根本不存在。
根因很典型：`build-flutter` 开头会先清空 `flutter\build`，被杀的构建留下的是空目录，
而管道末尾那行 `pushed <sha>` 看着像成功——**把"推分支成功"读成了"构建完成"**。
重建后改用产物断言确认：文件存在，且 mtime 晚于本次构建开始时间。

这条不是被推翻的结论，而是从上面几条里长出来的做法，写在这里因为它今天救了一次。

恢复 Android 构建时，如果只以"workflow 绿了"为验收标准，会得到一个**能装但一启动就崩**的
APK：没有任何环节把 `librustdesk.so` 放进 `jniLibs/`，而 `ffi.kt` 在 object 初始化里
`System.loadLibrary("rustdesk")`。所以那个 workflow 里有一步专门 `unzip -l` 断言
APK 内确实存在 `librustdesk.so` 与 `libc++_shared.so`，缺任一即失败。

**可复用的手段**：为"产物本身"写断言，而不是为"流程走完"写断言。
同理适用于安装器（装完要断言服务状态、配置内容、防火墙规则），以及 CI 的兜底
（前置 job 被跳过时会显示为灰色对勾，所以要有一个 `guard` job 把"跳过"变成红灯）。

## 9. 可以量的事实，不要猜

**结论**：本机内存被吃光，猜是编译机构建导致的（scp 管道缓冲，或本地并发的 flutter）。

**错在哪**：和构建一点关系没有。

**什么让人发现不对**：没有"发现"的时刻——是被要求"顺手查一下并说明"，才去量的。
这一点值得单独说：这条如果没人追问，会作为一个似是而非的解释留在记录里。

**怎么定的案**：`Get-Process` 直接量。本机 8 个 claude 进程合计 3,145 MB，
ssh 与 scp 两个进程合计 **22 MB**，本机没有任何 flutter/dart/cargo/rustc 进程，
整机 31.8 GB 只剩 1.4 GB。结论整个反转：是我们这些会话自己吃光了内存；
那个后台任务被杀只是因为它是后台任务、被挑中当软柿子，与它自身开销无关（11 MB）。

**可复用的手段**："谁占了内存/磁盘/端口"这类问题有一条命令就能给出答案，
猜测的成本反而更高。凡是能被一条命令量出来的事实，不要写猜测。

## 10. 一次失败的实验，默认结论是"我的方法错了"

**结论**：性能基线里记了一条待办——"codec-preference 写进用户默认文件后没有下发到被控端
（used preference: Auto），需要找到下发路径"。措辞暗示这是产品缺陷。

**错在哪**：没有这个缺陷。是实验方法错了——配置写错了文件。

**什么让人发现不对**：后来做上游盘点时顺手 grep 这个键，起了疑。

**怎么定的案**：全仓 grep 该键，只有一个读取点 `Decoder::preference`，它读的是
`PeerConfig::load(id).options`；再读 `PeerConfig::load` 确认它只读 `peers/<id>.toml`、
找不到就返回 `Default::default()`——**options 这个 map 根本不与用户默认合并**。
所以正确位置是被控端各自的 peer 文件。后来强制某编码器那一轮写对了位置就生效，反向印证。

**可复用的手段**：实验没出现预期结果时，先怀疑实验本身，而不是被测对象。
尤其当你打算把这个结果写进文档给别人看——一句"产品没有下发"会被后来者当成已知缺陷，
而它其实只是一次放错文件的操作。验证方式是把配置项从"读取点"反向追到"存储位置"，
而不是从"我写在哪"正向假设它会被读到。

## 11. 截图里的东西，未必是我们传过来的

**结论**：用户截图里黑底上铺满随机彩色矩形、中间一个巨大时间戳，据此报了"画面损坏"，
并怀疑是刚改的帧队列丢帧导致参考链断裂。

**错在哪**：把被控端桌面上正在跑的东西当成了传输结果。没有先问"这些像素在被控端本来长什么样"
就下了结论，等于把一张正常传输的截图判成了传输故障。

**什么让人发现不对**：同一帧里开始菜单的文字和图标是像素级清晰的——**解码坏帧不会只坏一部分
而放过另一部分**；而且那一轮日志里 `handle video frame error` 计数是 0。

**怎么定的案**：找到了性能测试用的动画夹具（黑色窗体、每 33 ms 画 60 个随机矩形、
48 号字的时间戳），与截图里的图案完全对应；停掉夹具重新拍一张干净桌面，渲染完全正常。

**可复用的手段**：判断"画面坏了"之前，先确定源端此刻本来应该显示什么。
另一个便宜的判据是**损坏的选择性**：真正的解码错误不会精确地只破坏一部分内容而让另一部分保持清晰。

## 12. 功能的名字，与它实际接触的网络端点不是一回事

**结论**：把"UDP 打洞"和"IPv6 打洞"归为同一类——"只联系我们自己的服务器"，
据此把两者都改成默认开启，并把这句话作为依据写进了项目规则。

**错在哪**：对 IPv6 打洞是错的。开启后，探测函数会向内置的公共 STUN 列表
（若干家第三方）发真实查询来获取本机公网 IPv6 地址。它和 WebRTC 同类，
都会接触用户从未选择的第三方。

**什么让人发现不对**：不是测试也不是评审——是为了给这个功能写说明文档，去读了探测函数的实现。
**如果只写代码不写文档，这个错误会带着依据它写下的规则一起上线。**

**怎么定的案**：读"什么都没配置时"那条分支的实现，而不是读功能名、也不是读它的注释。

**可复用的手段**：默认值管的正是"用户什么都没配"这个场景，而这个场景的行为最容易与功能名字不符
——"IPv6 打洞"听起来纯本地，实际要问公共 STUN。所以**验证默认行为要读未配置路径的实现**。
这条和第 10 条是同一个病根的两面：都是把"我以为的"当成"它实际做的"写进了文档，
区别只在一个写错了产品、一个写错了规则本身。成本是：一条错误事实被写进项目规则，
且改动违反了刚写下的规则，约一小时后才被发现。

## 13. 开关的读取点，和它要保护的行为不在同一侧

这一条与其余各条性质不同：它不是"谁判断错了"，而是**代码结构本身错了**，所以单列。

**现象**：被控端会向内置的公共 STUN 服务器发真实查询，去获取自己的公网 IPv6 地址。

**错在哪**：探测函数的三个调用点里有两个没有门控——被控侧的启动路径和 NAT 类型探测。
于是**一台机器联系哪些第三方，由对端的设置决定，而不是由它自己的设置决定**。
被控端往往还是无人值守的机器，主人更不知情。

**什么让人发现不对**：为了核对上一条那句话去读调用链，顺着就看到了被控侧那个无条件调用。
**前一个错误挡住了后一个错误的发现**——先误以为它不碰第三方，纠正之后顺藤摸瓜，才发现连门控都没有。

**怎么定的案**：把该函数的三个调用点全部列出来逐个看门控，而不是只看正在改的那一个。

**可复用的手段**：这类缺陷的识别信号是"**一个开关的读取点和它要保护的行为不在同一侧**"。
查法很机械：把开关的所有读取点、行为的所有触发点分别列出来，看有没有触发点不在读取点的保护下。
修法上有个通用选择：**门控放在能力的入口（咽喉），不要放在调用点**——调用点会增加，咽喉不会；
那次三个调用点漏了两个，正说明逐点加门控不可靠。修复带了一个断言：未启用时连尝试都不会被记录
（探测真体在碰网络前会写时间戳，时间戳没动就证明什么都没发出去）。

## 14. 验证隐私行为的测试，本身可能就是那个隐私行为

这条是今天最该记住的一条。

**结论**：要证明"改名后的构建不会向上游请求版本"，于是写了个测试直接调用检查更新的函数，
断言它不发请求。

**错在哪**：单元测试里 `APP_NAME` 还是默认值 `"RustDesk"`——真名是运行时由
`load_custom_client()` 才设上去的。所以在测试进程看来，**这就是上游的构建**，
那行调用会真的从构建机向上游 API 发出一次请求，带着设备指纹、操作系统、系统版本、CPU 架构。

**什么让人发现不对**：测试挂了，但不是挂在网络上，是挂在前面随手写的那句
`assert_ne!(get_app_name(), "RustDesk")` 上，它先一步拦住了。
**也就是说这次是侥幸**：如果没写那句断言，测试会"通过"，而每次 CI 都在替我们发一次请求。

**怎么定的案**：把判据抽成纯函数（`may_check_upstream_version_for(app_name)`），
对这个函数断言，不碰全局状态、也不碰网络。

**两条可复用的手段**：
* **测试环境的全局状态不等于运行时状态。** 这里是 `APP_NAME`，同类的还有配置单例、
  进程级缓存——凡是"启动时才初始化"的东西，在单元测试里都是出厂值。
  拿它们做判断的代码，在测试里走的是与线上不同的分支。
* **要验证"某件事不会发生"，不要通过执行它来验证。** 执行它意味着：如果判断写错了，
  它就真的发生了，而且发生在自己的构建机上、每跑一次 CI 就发生一次。
  正确做法是把"要不要做"的决策抽成纯函数，对决策断言，而不是对后果断言。

## 15. 只读一侧的调用链，就给"能不能走到"下结论

**结论**：审计里写"手动检查更新没有门控，用户点一下就会发指纹"。

**错在哪**：手动那条路径**根本不存在**——那个函数没有任何调用者，界面上也没有这个按钮。
只读了 Rust 侧的调用链，没去 Flutter 侧确认入口是否可达。

**什么让人发现不对**：去修的时候，找不到该修哪个按钮。

**真相比原结论更糟**：Windows 上"自动更新"开关的显示条件里，`!isCustomClient()`
只挂在 macOS 那一支，所以每个 Windows 安装版都显示它；用户勾一次，更新线程就定时发。
**不是"点一下发一次"，是"勾一次之后一直发"。** 原结论把严重性说小了，位置也说错了，两个方向都偏。

**可复用的手段**：判断一条路径是否可达，要走完**从界面到实现的全程**。
只看后端函数没有门控，可能它根本没人调用；而真正的入口在另一侧、长得完全不一样。
反过来也成立：一个没有调用者的函数，不值得为它写门控，先确认它是不是死代码。

## 23. 查"为什么不一致"之前，先确认两边是否都发生过

**情况**：桌面预览一张都没存下来。给出的三条候选原因分别是 `ready` 条件、30 秒节流、
以及存储 key 里含登录令牌导致每次登录换 key——三条都在回答同一个问题：
"**写进去的和读出来的为什么对不上**"。另一个会话已经准备从存取那一头对撞着查 key 怎么拼。

**实际做法**：先不查原因，先去看那个目录。结果是**目录存在，但里面 0 个文件**。
目录存在说明读路径跑过（每 5 秒一次的 `load` 会 `create(recursive: true)`），
0 个文件说明写路径从未到达。

**这一步值多少**：它把问题从"读写不匹配"直接切成"写根本没发生"，
于是三条候选里的两条（key 拼接、令牌变化）当场出局——它们解释的是"写了但读不到"，
而写从来就没发生过。对撞查 key 的那半工作也不必做了，因为它的前提不成立。

**可复用的手段**：**在查"两边为什么不一致"之前，先分别确认两边是否都发生过。**
一个只在一侧存在的事实，比任何关于两侧关系的推理都便宜。
具体到文件、缓存、数据库这类有痕迹的东西，"有没有产物"往往一条命令就能回答，
而它能一次排除掉半个问题空间。

## 24. `catch` 里设退避，会把持续失败伪装成正常等待

**情况**：上面那个预览捕获，每次都在同一行抛异常，但外面是这样接的：

```dart
} catch (e) {
  debugPrint('Desktop preview capture failed: $e');
  _lastCapture = DateTime.now();   // 30 秒退避
}
```

**它造成了什么**：异常本身被 `debugPrint` 消化掉（release 下多半看不到），
而退避时间戳被设上，于是下一次调用因为"距上次不足 30 秒"直接返回。
从外部看，这套逻辑的行为是"每 30 秒安静地试一次"——**与"还没到时候"完全一样**。
真相是每一次都失败，而且永远都会失败。

**可复用的手段**：
* `catch` 里如果要设置退避、节流或重试间隔，**至少要让失败本身可见**：
  记一个连续失败计数、或把第一次异常按更高级别记一次。
  "静默 + 退避"的组合会把永久故障变成看不出来的等待。
* 判断一段代码"是不是在正常等待"时，去找**它有没有成功过一次**的证据，
  而不是看它有没有在报错——设计得体面的退避恰恰不报错。

## 25. 把错误转写成一个合法值，它就不再是错误，只是一个不对的结果

今天有四件事是同一个形状，值得合起来看。

* **预览捕获**（第 24 条）：异常被 `catch` 吞掉并设上 30 秒退避，**永久失败变成了"这次没存"**。
* **被否掉的默认值方案**：给共享控件的调色板参数加默认值、不传就用亮色常量。
  失败方式是**深色下某个控件仍然是亮色**——没有编译错误、没有异常、没有日志，
  只有人眼在某次截图里偶然发现。这比编译错误难查一个数量级，所以这个方案被否了。
* **`translate()` 在桥接缺失时返回 key 本身**：形状相同，但它有一条别的没有的辩护——
  **返回值本身是有意义的**（key 就是英文原文，所以那是英文渲染，不是占位符）。
  即便如此仍补了一次性 warn 日志，理由是：值有意义**和**事件有痕迹，要两面都占住。
* **工具给出过期答案**（见下条）：格式完全正常，只是对应的是上一个提交。

**共同点**：错误被转写成了一个合法值或一次无害的重试，于是它不再触发任何机制——
不报错、不抛出、不记录，**只是给出一个不对的结果**。

**判据**：设计兜底时问两个问题。
① **这个兜底值本身有意义吗？**（"英文原文"有意义；"深色下的亮色"不是任何人想要的渲染。）
② **这件事发生过，有痕迹吗？** 两个都满足才是好兜底；
只满足①是可接受但要补痕迹；一个都不满足的，宁可让它报错。

## 26. 工具的输出如果不能自证对应哪个输入，先给它加出处

**现场**：编译机上的 `fanalyze.ps1` / `ftest.ps1` 只切到 `wt-<分支>` 目录就跑，
**不更新工作树**。于是推送之后直接跑，读到的是**上一个提交**的结果。
它不报错、不警告，沉默地给出一个过期但格式完全正常的答案。

**它骗了谁**：同一天骗了两个人——一个以为自己的修复没生效，另一个以为对方报的错还没修。
两人都据此发了消息，互相以为对方那边有问题。

**修法之争**：最初的做法是加一段注释头说明"要先 checkout"。注释写了，但更管用的是另一件事：
**两个脚本现在第一行打印 `worktree at: <短哈希> <提交标题>`**。
注释要人主动去读，这一行每次都撞在眼前。

**判据**：**如果一个工具的输出无法自证它对应哪个输入，先给它加出处，再考虑加说明。**
出处是每次都在的，说明是需要人记得去看的。

## 27. 局部变量名遮蔽了库前缀

小而具体，但错误信息完全不指向真相，所以值得记一笔。

**现场**：把 `UiColor.x` 换成 `ui.x` 时，局部变量取名 `ui`。
而那个库的头部有 `import 'dart:ui' as ui;`——**局部名把库前缀遮住了**。

**它报成什么**：`The getter 'PointerDeviceKind' isn't defined for the type 'UiPalette'`。
报错位置在一处我根本没改过的、判断指针类型的代码上，而且听起来像是调色板缺了个成员。

**可复用的手段**：给"取一次存起来"的局部变量命名时，避开常见的库前缀
（`ui`、`math`、`io`、`async`、`html`）。这次改叫 `pal`。
更一般地：**当错误信息指向一处你没有改过的代码、而且说的是一件不可能的事时，
先怀疑名字撞了**，而不是去读那处代码。

## 28. 一个名字承担两个职责时，"它该是多少"就永远吵不完

**现场**：量深色对比度时发现，白字压在深色 `primary` 上只有 3.47:1，而 13px 文字需要 4.5。
想把它调亮、调暗都有**真实的理由**——这个颜色在深色表面上当文字时要够亮，
当填充底托白字时要够暗。折中的结果是两边都不达标，而且没人能说清它究竟该是多少。

**根因不是取值挑得不好，是两个职责共用了一个名字。** 答案是拆：
`primary` 留给"把主色当文字或图标颜色"，新增 `primaryFill` 给"填充 + 上面压 `onPrimary` 内容"。
原名留给已经读得对的那一侧，所以亮色一行没改，迁移成本只落在本来就有问题的那一侧。

**判据**：**当出现"这个值该是多少"的争论、而且两边都有真实理由时，
该想到的是拆名字，不是继续调数值。**

**这不限于颜色**。同一个形状还包括：一个超时被一个调用方要求短、另一个要求长；
一个配置键对两个子系统意味着两件事；一个函数的两批调用方想要相反的默认值。
共同点是**争论持续不下且双方都对**——那通常说明争的不是取值，是这个名字指了两件事。
（起因与完整推导见 `docs/dark-token-decision.md`。）

## 29. `const` 陷阱：报错位置不是出错位置

**现场**：`static const` 改成 `of(context)` 之后，凡把它用在 `const` 构造里的地方全部失效。
今天三个人各撞一次。

**为什么难定位**：**分析器报的位置是 `const` 构造处，不是取值处**，
而且同一行往往还有个仍然合法的 `static const` 尺寸参数，读起来像整个 widget 都错了。
还有一种变体报成 `const_eval_method_invocation`（因为 `of(context)` 是方法调用），是同一个病。

**定位法**：换完之后**先扫一遍，别逐个 analyze 撞**。单行的用 `grep -n "const .*ui\."`；
跨行的要找 `const 大写开头(` 之后、配对括号内出现 `of(context)` 的整段。

## 30. grep 命中是候选，不是结论

**现场**：扫剩余待迁移文件时，`peer_card.dart`、`peer_tab_page/`、`peers_view/` 三处命中，
看着像漏网。实际命中的是 `PeerUiType` 这个**同名前缀**——那几个文件一处 token 都没用。

**可复用的手段**：**字符串匹配给出的是候选，不是结论**；动手之前打开看一眼，
比迁完再回滚便宜。这与"目录存在但 0 个文件"那次（第 23 条）是同一族：**先核前提，再查原因**。

## 31. 顶层 helper 拿调色板：传值还是传 context

**两种写法都对，代价不同**：
* **传解析好的值**（`uiDialogButton(UiPalette ui, UiTypeset type, ...)`）更干净——
  `of(context)` 除了查找还会把调用方注册为该 InheritedWidget 的依赖，
  每个 helper 各查一次，主题切换时重建更密。
* **传 `BuildContext`** 的协调成本更低——如果签名里本来就有 context，调用点一行都不用改。

**判据不是哪个更好，是这个 helper 有几个调用点、跨不跨人。**
设置页那七个 helper 全在一个人手里，两种写法都无所谓；
而 `ui_fields.dart` 那三个函数跨了 6 个文件 9 个调用点，
改签名就成了**跨会话协调**——这才显出传值那一侧的代价。

## 32. 诊断基线的数字本身就是探测器

**现场**：迁移调色板时，两个人各踩了同一个温和的坑——多加了一行
`import 'ui_palette.dart'`。解析入口 `UiColor.of` / `UiType.of` 其实在 `ui_tokens.dart` 里，
只有当 `UiPalette` / `UiTypeset` **作为类型名**出现时（例如给顶层函数加参数）才需要导入它。

**它为什么容易漏**：失败方式是 `unused_import` **warning，不是 error**。
它不拦任何人，只让诊断数悄悄 +1。两次都是**靠数字动了才发现的**：222 变 223、222 变 226。

**这个方法比这个坑本身通用得多**。今天靠数字变化抓到的至少三次：
`222→226`（const 陷阱连锁加上这个 import）、`222→238`（设置页 helper 缺 context）、
`222→224`（另一处 const 陷阱）。**持平才算干净，涨了就得去看是不是自己的。**

**但它有一个前提，而且很容易被破坏**：**基线必须是一个人人都知道的确切数字**。
一旦有人开始说"大概两百多条"，探测器立刻失效。所以配套的规矩是
**报 analyze 结果时报确切数字，不要报约数**。

**还有一条同源的观察**：一次改动引入的多条诊断里，**最扎眼的那条会掩护其余的**。
当时那 4 条里 3 条是 `const` 陷阱的连锁 error，1 条是这个 warning；
盯着 error 看的人很容易把 warning 一起忽略过去。
所以清的时候要按**数量**对账，而不是按"最严重的那条修好了没有"。

## 33. 「从未被使用」可能不是死代码，是忘了接的功能

**这条最值钱**，因为它把一条最容易被当噪音清掉的告警，变成了功能缺陷的线索。

**现场**：做读写分离时分几步走，中间几步模块还没接线，会产生一堆"从未被使用"。
于是在模块头加了 `#![allow(dead_code)]`，并写明"下一个提交接线时删掉"。
接线完成后撤掉 allow，冒出两条：一条是真多余，删了；
**另一条是 `Writer::close` 从未被使用——它不是多余的代码，是忘了接的收尾**。

**它的后果**：写任务只在 socket 出错时结束，于是**一个正常结束的会话会把写任务留着**，
直到 socket 自己报错；对端如果只是闲着，那可能是很久。

原话：

> **`close` 方法"从未被使用"这条告警指的不是死代码，是漏接的功能；
> 图省事留着 allow，这个泄漏就留在产品里了。**

**怎么读这条告警**：当成**两种可能**——多余的代码，或者忘了接的功能。
区分方法很简单：**问"这个东西当初是为什么写的"**。
`close` 当初是为了结束写任务，那就说明"结束写任务"这件事现在没人做。

**关于临时 allow**：加可以，但**必须在同一批工作里撤掉并逐条读**。
撤掉它的动力来自一条自己定的规矩——"每个提交都不能新增告警"。
没有这条规矩，"临时"就会变成"永远"，而且**之后没有任何东西会再提醒你**。

## 34. 工具的开关在缩小它做的事，而它不报告自己没做什么

**现场一**：用 `check.ps1 <分支> -Tests` 验证改动，看到编译通过、没有报错，
以为测试过了。实际上 `-Tests` 只做 `cargo check --tests`，**只编译不运行**；
要运行必须再加 `-Run <过滤>`。"编译通过、没有 test result 行"的真实含义是
**一个测试都没跑**。

**现场二（同一天，同族）**：删掉一个多余方法后跑 `-Full`（不带 `-Tests`），零错误。
但不带 `-Tests` 根本不编译测试，而那个方法正被它自己的测试用着。
这次**没有被及时发现，是后来被真实测试抓住的**。

**可复用的手段**：**把"没有出现的输出"当成信号**。
期望跑测试就必须看到 `test result:` 那一行，看不到就是没跑，
**不管返回码多干净**。工具已改为在无 `-Run` 时打印 `compiled only; pass -Run to execute`
——这与第 26 条同源：**让输出自证它做了什么，而不是让人记得它不做什么**。

## 35. 过滤器让你看到的比实际少

**现场**：用 `-Run 'connection'` 跑测试，看到一个红，据此报告"master 上有一个红测试"。
换成更准确的过滤 `-Run 'port_forward_mux::tests::tunnel'` 之后，真相是 **17 个里 9 个红**。
**报出去的数字差了九倍，而当时是有把握的。**

**它与第 34 条的区别**：第 34 条是**工具没做你以为它做的事**；
这条是**工具做了你要求的事，只是你要求的范围比你以为的窄**。
**后者更隐蔽，因为工具的行为完全正确**——没有任何地方出错。

**可复用的手段**：
* **先不加过滤跑一次全集，再缩小**。
* 报告数量时**说清楚"在什么范围内"**。"connection 过滤下 1 个红"是真话，
  "master 上 1 个红"是假话——当时说的是后者。这与第 19 条相通：
  **具体到能被证伪的程度，包括说清楚这个数字的取值范围**。

---

**这三条与本文档许多条的共同点**：它们都是**沉默的失败**——
工具不报错、告警看起来无害、过滤器工作完全正常。
真正会主动喊出来的问题反而都很快被解决了。
**本文档里绝大多数条目，讲的都是不喊的那一类。**

## 36. 时间窗错了会朝哪边错

以下三条都来自同一个脚本的**第一次运行**（`scripts/wan-smoke.ps1`，我写的，
写完到那天为止一次都没跑过）。三种假 PASS 形态不同，所以分开记。

**现场**：脚本抓服务端日志时，用 `(Get-Date).ToUniversalTime()` 拼一个墙钟字符串
交给 `journalctl --since`。而 `journalctl` 按**服务器本地时区**解释它，
服务器是 `+0800`，于是窗口往前多开了八小时。

**为什么这不是"多看了一点"**：判定方式是"日志里出现过某事件即 PASS"。
多开的八小时里有**几小时前别人会话留下的事件**，
于是它可能匹配到一条与本次运行毫无关系的记录**而判通过**。

**判据**：**时间窗开小只会漏报，开大会误报。**
漏报会被人追查，误报会被当成成功收走——两个方向的风险不对称。
写任何窗口、阈值、重试次数时先问一句：**错了会朝哪边错。**

**修法**：改用纪元秒（`--since '@<秒>'`），两端时区都无法误读；
并且在服务器上先验证过这个写法可用，而不是假设。

## 37. 「这行必须不出现」对不存在的文件返回真

**现场**：脚本用 `-not (Test-Line $file $pattern)` 表达"这条日志必须不出现"。
而 `Test-Line` 的实现是：**文件不存在就返回 `$false`**。
于是文件不存在时 `-not $false` 就是 `$true`——**PASS**。

**而文件不存在恰恰是取证彻底失败的样子**：过滤没命中时 `Set-Content` 根本不创建文件。
**一次连不上服务器的运行，会让三条否定式检查一起变绿。**

**原话**：

> **「看不到」不等于「不存在」，读不到就该 FAIL 而不是 PASS。**

**它为什么最隐蔽**：这不是"证据消失了"，是**取证这一步失败了，却被算作证据**。
前者至少会少一条日志让人起疑；后者外表和成功一模一样。

**修法要两件事，缺一不可**：日志即使为空也写出文件，于是**文件存在 = 看过了**；
另加一个 `Test-NoLine`，读不到就判 FAIL。
只加后者的话文件依然不存在，只是从假 PASS 变成永远 FAIL。

## 38. 否定式断言必须先证明观测面存在

**现场**：脚本里有一条 `T1 'hbbs: nat_type not symmetric'`，
判据是"日志里不出现 `decision=punch.*nat_type=SYMMETRIC`"。它在同网段下稳稳地 PASS。

**问题**：`nat_type` 这个字段**只打在 `decision=punch` 那一行上**，
而同网段时服务端走的是 `decision=local_addr`，那一行根本不会产生。
于是"没匹配到"成了"通过"——**它通过不是因为 NAT 不是对称的，是因为压根没有东西可看。**

**是怎么发现的**：没有只看整体命中数（过滤式一共命中 431 行，看着很健康），
而是**逐个模式单独数了一遍**：`event=punch_hole` 142、`event=relay_request` 73、
`got paired` 66，但 **`decision=punch` 0、`event=relay_peer_ticket` 0**。
然后回服务端源码核对，确认这两个字符串**确实存在**（不是写错了），只是同网段到不了那一行。

**判据**：**一个否定式断言，必须先证明它的观测面存在。**
做法就是上面那一步——不要只看聚合的命中数，**逐条确认每个模式至少在某种情况下真的出现过**；
一个从未出现过的模式，它的否定式断言是空的。

**它为什么最像"验证过了"**：它是绿的、无害的、完全符合预期。
第 36、37 条至少需要某种失败才触发，**这一条在一切正常时也一直是假的**。

**一个属于我自己的注脚**：这三种假 PASS 能在同一个文件里共存，
是因为那个脚本**从写好到被人运行为止，一次都没执行过**。
它属于"从未被执行过的验证"那一族——**没跑过的东西，不会因为看起来合理就是对的**，
而我写它的时候确实觉得它很合理。

## 预防：在拿到结果之前，先把判据定下来

前面十五条都是"错了之后是怎么被发现的"。下面两条性质相反，是**怎么让错误无处可躲**——
它们不靠事后复核，而是靠提前把话说死。

两条的解药其实是同一个：**在拿到结果之前先定判据**。判据先定，"证实"和"什么都不用改"
就都是合法结局；判据要是事后定的，人就会挑一个自己喜欢的结局。急着下结论和忍不住要产出，
压力方向相反，根子都是"想要有个结果"。

### 16. 预先写好否定自己结论的判据

**做法**：认定某台虚机整场会话掉进 GDI 的原因是桌面表面映射被拒（该机型的合成显卡正会如此），
据此改了代码并加了一条新日志。验证不由自己跑——跑的人在另一台机器上、自己不在场。

**它防住了什么**：防住在验证阶段把结果往自己的结论上靠。如果判据只写"看新日志行出不出现"，
出现就算证实，不出现则很容易被解释成"环境不对、再跑一次"，结论就永远不会被推翻。

**具体怎么操作**：在清单里把**三种结果全部写死，而且三种都写明"可报"**：
①新行出现、旧的回退行消失 = 证实；
②**新行不出现、旧行照旧 = 原因是别的，改动是惰性的，回去看帧释放路径**；
③两条都出现 = 还有第三条分支，把周围日志发来。
另外对执行的人明说了一句"不会替我留面子"——②那种结果如果被含糊过去，
提出结论的人会在错的方向上多花一天。

### 17. 干净就报干净，不为产出而改

**做法**：读代码判断会话结束时资源是会归还的（采集循环在最后一次取消订阅后一帧内退出，
采集器与编码器随它走，音频设备在服务重置里释放，每连接的线程随通道结束，
连接管理器是独立进程会自己退出）。

**它防住了什么**：防住"既然排了一项测量，就得有个改动来证明这项没白排"。
写清单的时候就预计这一项大概率是干净的——**那正是最容易硬找一个地方改一下的时候**。

**具体怎么操作**：把这句直接写进判据里——**"If it is clean, say so and change nothing."**
同时写明为什么仍要测而不是靠推理：唯一没把握的是 DXGI 与硬件编码器的句柄和内存会不会回来，
所以这一项是**测**而不是**论**。范围先收窄到真正不确定的那一块，剩下的说清楚是推理，
干净就更容易被报成干净。

### 21. 待办上的前置条件，和正文一样会过期

（本条后加，所以编号排在第三组之后，但它属于预防组。）

**现象**：`docs/backlog.md` 里有两条待办，各自写着一个前置条件——
"先定夺深色是否为受支持的外观"、"移动端能构建，否则工作看不见"。
去改措辞时才发现，**两个障碍都已经不存在了**：深色的裁定当天早些时候就做了，
机制也定了；移动端当天下午起就能构建了。两条都在**等一个已经消失的障碍**。

**为什么会这样**：待办特有的一种腐烂方式——条目写下的那一刻是准确的，
然后世界变了，而条目不会自己更新，于是它一直显示为"被挡住"。
**正文说的是要做什么，容易被复核；前置条件说的是为什么还不能做，没人会去看它。**

**协调方的话**：

> **待办上的前置条件要和条目正文一样定期复核，否则它会把已经能做的事一直标成做不了。**

**可复用的手段**：
* 复核待办时，**前置条件要单独过一遍**，问的是"这个障碍今天还在吗"，
  而不是"这件事该不该做"。
* 把前置写成**缺什么**而不是**等什么**（"缺一台 Android 设备"而不是"等移动端可构建"）。
  缺什么是可核对的事实，等什么是一种状态描述，状态会变而描述不会。
* 前置解除时，**不要删掉原来的措辞**，写明它曾经是前置、现在为什么不是。
  否则"当初为什么把这件事排在后面"就没有答案了——而那个理由往往比结论更有参考价值。
* **最可执行的一条，由协调方提出**：**解除某个障碍时，同时去搜还有谁在等它。**
  它把复核从"定期要做的事"变成"某个动作的固定后半段"，而定期要做的事最容易被跳过。
  协调方给自己定的规矩是：**每做一次解除障碍的裁定，在同一条消息里问一句"还有谁在等这个"**。
  当天有两个现成例证：深色受支持的裁定、Android 恢复可构建，两次都没人去搜谁在等，
  于是两条待办一直冻着，直到有人为了改措辞才顺带发现。

## 39. 「尚未验证」的标注必须带解除条件

**现场**：一天下来写了很多"尚未验证""待补""受限于环境"的标注。
绝大多数只说了**为什么现在不行**，没说**什么条件下可以**。

**问题**：一条没有解除条件的标注，**会从警示退化成装饰**。
读的人无法判断它是"今天做不了"还是"永远做不了"，
也无法在条件到位时认出来——于是它一直挂着，最后没人读。
这与第 21 条（待办的前置条件会过期）是一枚硬币的两面：
那条说的是前置解除了没人发现，这条说的是**前置压根没写下来**。

**触发这次整理的例子**：有人在一个脚本的状态段里写了
"直到有人跑过这三个用例并在这里说明"——**它给出了摘掉这个状态的条件**，
于是那条标注是可终结的。对照之下，同一天其它标注大多不是。

**做法**：每条标注补一句"满足什么条件即可摘掉"，
并按第 21 条的形态写成**缺什么**而不是**等什么**：
缺一台 Android 设备、缺一个 HDMI 假负载、缺一次异网出口、
缺某人关掉他自己的窗口、缺某人跑过并在此说明。
**缺什么是可核对的事实，等什么只是一种状态描述。**

**整理时的两条纪律**：
* **不要顺手改标注本身的结论**——补的是解除条件，不是重新判断。
* **不要把没有解除条件的条目删掉**——缺条件本身就是发现，补上即可。

## 40. 一条规则漏掉了明显同类的东西，先怀疑判据划错了

**现场**（由 51 提出并修正）：共享工作树里有一条禁令——
`--amend` 和 `rebase` 一律不用，因为 HEAD 随时可能不是你的提交。
后来有人在同一个工作树里跑了 `git stash` + `pop`，把别人未提交的改动卷进去又弹回来
（那次无损，事后核过），并主动指出：**规则里漏了 `stash`**。

**为什么会漏**：当初的边界是按"**会改写提交历史的操作**"划的。
`stash` 不改写历史，所以它**根本没进视野**。

**而它的危害面反而更大**：`stash` 动的是别人**未提交**的改动。
提交被改写至少还能从 reflog 找回来；**未提交的东西弹错了就没了。**

**正确的判据**：不是"任何会改写提交历史的操作"，而是
**"任何会移动或丢弃别人未提交改动的操作"**。

**为什么不能只补一个命令名**：如果只在列表里加上 `stash`，
**下一个漏掉的会是 `git checkout -- <path>` 或 `git restore`**——
它们同样不碰历史，同样能一声不响地抹掉别人的改动。
**列命令是穷举，说边界才是规则。**

**可复用的手段**：**当一条规则漏掉了一个明显同类的东西，
先怀疑判据划错了，而不是往列表里补一项。** 补列表只能挡住已经出过事的那一个。

**它与"动作式规则"那条并不矛盾**：动作要具体到可执行，
**边界要抽象到能覆盖没想到的情况**——具体的是"做什么"，抽象的是"什么时候适用"。

## 41. 给理由时说取舍，不要只说后果

**现场**（由 51 提出）：给烟测脚本加了"有客户端在跑就拒绝启动"这个行为。
解释理由时说的是：**一个还连着的客户端会抢走会话、也会污染日志。**
协调方的说法则是：

> **让它更难跑一点，好过让它跑出不可信的绿。**

**区别在哪**：前一句说的是**后果**——它解释了这一次为什么要拒绝。
后一句说的是**取舍**——它给出的是在"易用"和"结果可信"之间怎么选。

**为什么取舍更有用**：**后果只对这一个决定有效，换个场景就用不上了；取舍可以迁移。**
下一个人面对"要不要加一道会让人嫌麻烦的检查"时，
用不上"会抢会话"，但用得上"更难跑好过不可信的绿"。

**怎么做**：写决定的理由时，写完后果再问一句——
**"如果换一个完全不同的功能，这条理由还站得住吗？"**
站不住，就说明写的是后果，得再往上抽一层。

## 42. 判据要对每个执行者都有够得到的检查点

**现场**（由 51 提供）：改了 `libs/base/Cargo.toml` 的依赖却没提交 `Cargo.lock`，
把 GitHub 上的 Linux 门禁卡住了——**卡的是所有人的检查，不只是自己那一次提交**。
随后定的规则是：改了任何 `Cargo.toml` 的依赖就必须同时提交 `Cargo.lock`，
判据写成"本地 `cargo check --locked` 能过"。

**问题在哪**：这条判据对 51 **等于没有检查点**。它不在本地跑 cargo，用的是编译机的
`check.ps1`，而**那个脚本不带 `--locked`**。照着规则做也发现不了问题——
规则描述的那个动作，它根本执行不了。

**根因**：写判据的人默认了**自己的工作方式**。规则本身是对的，
坏的是它假设了执行者的工具链。

**怎么做**：定规则时多问一句——**"这条对每个执行者都有可执行的检查点吗？"**
某类执行者够不到那个检查点，要么换一个人人都够得到的判据，
要么把检查点做进他们真正会用的工具里。这次是两条并用：
**给编译机脚本加上 `--locked`（机器替你看），
另加一条不依赖任何构建工具的兜底——改了依赖后 `git status` 里必须同时出现 `Cargo.lock`，
没出现就说明更新发生在别处，你提交的是半截改动。**

**与前一条的关系**：「规则挡不住忘了执行规则，检查点才能」说的是要有检查点；
这条更前一步——**检查点还得是执行者真的够得到的那一个。**

## 43. 去看它实际产生了什么，而不是看它有没有报错

**现场**（由 51 提供）：同一个工具上栽了四次，方向还不一样。

**做得比以为的少**（三次）：`check.ps1 -Tests` 只编译测试、不运行，
看到"没有报错"就以为跑过了；`check.ps1 -Full` 不带 `-Tests` 根本不编译测试，
删掉一个方法后看到零错误，而那个方法正被它自己的测试用着；
`-Run 'connection'` 按名字过滤，只有一个用例碰巧匹配，
于是"一个红测试"实际是九个。

**做得比以为的多**（一次）：改了依赖后在编译机上跑 `check.ps1` 是**绿的**——
因为 cargo 会**静默地把锁文件更新在编译机的工作树里**，那份更新随工作树丢弃。
**看到的绿，是靠一个看不见的自动修复换来的**，而门禁不允许这个修复。

**判据**：两个方向都靠同一件事暴露——
**去看它实际产生了什么，而不是看它有没有报错。**

**具体怎么操作**：

* 期望跑测试，就去找 `test result:` 那一行；没有那行就是没跑，退出码多干净都不算。
* 期望产生文件，就去 `ls` 那个文件；**目录存在但里面 0 个文件**这种事今天也发生过。
* 期望只改了 A，就去 `git status`；**多出来的 B，或者该出现却没出现的 B，都是信号。**

**为什么这一条能统住四次**：报错是工具**愿意告诉你**的部分，
产物是它**实际做过**的部分。前者由工具的作者决定，后者由现实决定。
工具没有义务告诉你它跳过了什么、或者替你补了什么。

**它与第 42 条是同一件事的两端**：这条说的是**别人的工具不会如实汇报**，
第 42 条说的是**自己写的规则也不会**——写"本地 `cargo check --locked` 能过"时，
同样没有汇报它隐含的前提是"你在本地跑 cargo"。

## 44. 一个数字只有在它的范围就是你的改动时，才是对你的改动的评价

这一条不属于"工具少说了什么"那一族（第 43 条）。这两次里工具**什么都没少说**：
`228` 是准确的，`222` 是准确的，差值 `6` 也是准确的。
**坏的是那个数字回答的不是提问的人问的那个问题。**

**范围偏宽的一次**（本会话）：改完远程工具栏跑 `flutter analyze`，看到 228，
上一轮记的基线是 222。按"多了 6 条"的读法，这一轮改动引入了 6 个错误。
实际上共享工作树里同时有好几个会话的在途改动，
那 6 条全是 `mainImportConfigText` / `mainPreviewConfigText` /
`mainEncodeShareConfig*` 在 `RustdeskImpl` 上未定义——别人还没生成 bridge，
和被碰过的 `remote_toolbar/` 一行关系都没有。
**问的是"我引入了什么"，答的是"这棵树上现在一共有多少"。**

**范围偏窄的一次**（51）：报"master 上有一个红测试"，实际是九个。
`-Run 'connection'` 按名字过滤，只有一个用例碰巧匹配，
于是**拿缩窄后的范围说了一句关于全局的话**。

**同一个毛病的两个方向**：**说出来的范围和心里想的范围不是同一个。**
一个把九说成一，一个会把别人的六算到自己头上。

**判据**：**共享工作树里的全局计数是所有人在途工作的和，差值不可归属。**
要归属就**按身份比，不按数量比**——看多出来的那几条**具体是什么**，
落在谁的文件、谁的符号上。

**可执行的问法**：在共享树里，"比基线多几条"这个问题本身问不出答案。
能问出答案的是——**这几条的身份里，有没有一条落在我碰过的文件或符号上？**
没有就是零，有就逐条看。这个问法不依赖基线准不准，
也不依赖别人是不是正在同时改。

**它给"报数字带范围"补了一个更强的理由**：约定里"报完成带哈希、报数量带范围"，
**带哈希防的是别人伪造，带范围防的是自己**——
不带范围的数字，连它在说谁都不确定。

**与第 32 条的关系**：第 32 条说基线数字本身是个探测器，
但那个前提比"基线只属于你"还要强一格（51 收紧）——
**还得是它在你两次测量之间没有动过。**
这次就是活例：`222` 与 `228` 之间，别人往同一棵树里落了在途的 bridge 改动。
**即使那个基线原本完全属于你，它也已经在两次测量之间移动了。**

**为什么这一格必须写出来**：读到"计数里混了别人的量"，
最自然的自救动作是"那我先测一遍当作自己的基线，再改，再测"。
**在共享树里这个动作同样不成立**，而且它看上去严谨得多，所以更容易被采信。
共享树里的基线不是一个数，是一个随时在动的量，两次测量根本不在同一个树状态上，
**不可比**。堵法还是同一个：**按身份对账，不按数量对账**——
身份不受别人落了什么影响，数量受。

## 45. 两台机器对同一个提交给出不同结论时，差异一定在版本控制之外

**现场**（由 52 提炼，起因是第 44 条那 6 个 error）：本机 `flutter analyze` 有 6 个
error，全是 `mainImportConfigText` / `mainPreviewConfigText` /
`mainEncodeShareConfig*` 在 `RustdeskImpl` 上未定义。当时的判断是
"别人还没生成 bridge 的在途改动"——**这个判断只有前半句对**。

**实际是什么**：`flutter/lib/generated_bridge.dart` 是生成文件，
被 `flutter/.gitignore` 第 44 行忽略，**根本不在版本控制里**。
本机那一份停在 2026-09-12，里面 `mainImportConfigText` 出现 0 次。
编译机的干净工作树上，**同一个提交**是 222 个问题、零 error。

**所以那 6 条永远不会因为谁提交而消失**——没有任何一次提交能改变一个不被跟踪的文件。
"等别人把 bridge 生成了就好了"这个预期本身就是错的，
错在它假设了差异来自某个还没落地的提交。

**判据**：**当两台机器对同一个提交给出不同结论时，差异必然来自不在版本控制里的东西**——
生成文件、构建缓存、环境变量、本地配置、未跟踪的文件。
**不要在提交历史里找原因，去比不受提交管辖的那一层。**

**可执行的动作**：结论不一致时，先对被指认的那个符号问三件事——
`git check-ignore -v <文件>`、`git ls-files --error-unmatch <文件>`、
以及那个文件的时间戳。三者任一说明它不受跟踪，就到此为止，
**不必再去比对方的提交**。

**为什么在 diff 里找不到**：`flutter analyze` **量的是一个工作目录，不是一个提交**，
而那个目录里有一批不被任何提交包含的文件。调用那三个符号的文件几小时前就推走了，
两台机器的差别自始至终不在提交里。

**它与第 44 条的关系**：第 44 条讲**数字的范围**（它统计的是谁的改动），
这一条讲**数字的产地**（它是在哪台机器、哪份未跟踪的输入上算出来的）。
两条合起来才覆盖同一个问题：**这个数字能不能回答我问的那件事。**
更细一层的区别（52 指出）：44 条说"说出来的范围和心里想的范围不是同一个"，
这条说"**同一个范围在两个地方不是同一堆字节**"。
**44 条能靠看命令参数发现，这一条在任何一台机器上单独看都发现不了**——
它只在两台机器对比时才显形。所以判据只能是"**两台机器不一致**"这个事件本身，
而不是任何一次读数。还有一层（52 指出）：
**44 条的错误在提问的人身上，45 条的错误不在任何人身上**——
两台机器都没做错事，字节就是不一样。
所以 44 条可以靠"问清楚自己在问什么"避免，
45 条只能靠"**发现不一致时不要先怀疑代码**"。
这也是为什么这一条的动作是三个 git 命令，而不是读 diff。

**由此定下的规矩**：本地 `flutter analyze` 的读数**不作为验收判据**，
以编译机干净工作树上的数为准；也不要在本地跑生成去"修"这个读数——
它不影响任何提交，也不影响 CI，只影响读数。这句同时写在
`docs/dark-acceptance.md` 的基线一节，否则下一个人在本地量出 228
会以为自己弄坏了什么。

## 45b. 同一棵树在两个时刻也不是同一堆字节

第 45 条讲**两台机器**，这一条把它从空间挪到时间：**同一台机器、同一棵树、
相隔几十秒的两次观察，同样可以互相矛盾而两次都是真的。**

**现场**（本会话与 0f）：我跑 `git diff docs/lessons-2026-09-13.md`，看到 68 行
未提交新增，据此说"0f 正在写第 48 条"。0f 跑 `git status` 看到文件干净，据此说
"我没有未提交内容"。两句话都基于自己手里的命令输出，两句话都是真的：

```
f7093f3ad  2026-09-14T00:02:26+08:00   （那段内容被提交）
4d34e4a9c  2026-09-14T00:02:30+08:00   （重号被整理）
git status 2026-09-14T00:03:22+08:00   （工作树已干净）
```

**我看到的和它看到的，中间隔着不到一分钟的一次提交。** 共享工作树上随时有别人的
在途改动，`git status` / `git diff` 的答案**只在读它的那一秒成立**。

**两个人各犯了一半**：我把一个瞬时读数当成了"谁正在做什么"的结论（而且作者是推断的，
见下），0f 用另一个瞬时读数去**否定**我的瞬时读数，并且当成了定论。后者更隐蔽，
因为**手里确实有命令输出，输出也确实是那样**。

**动作**：

* **陈述工作树状态时带上你读它的时间**，或者干脆不要陈述工作树，
  **改为引用一个提交 sha**——sha 不会随时间变，`git status` 会。
* **不要用自己的瞬时读数去否定别人的瞬时读数。** 先问"你是什么时候看的"，
  两个时刻之间发生过提交，两句话就可以同时为真。

**一个结构性事实，它让"去查作者"这条路在本仓库走不通**：所有会话的提交作者都是
同一个身份（`VocabVictor <83048106+...>`），所以 `git log` 的作者字段**分辨不出
是谁写的**。当时就算去查，看到的也只是同一个名字。**能分辨的只有提交主题、
改动路径，和当事人自己说。** 所以本条的动作不是"去查是谁"，而是
**不要替别人陈述他正在做什么**——问一句比查一遍可靠。

**归属的权威来源是派单，不是提交记录。** 同一天的第二次:有人问
"`1788fc264` 是不是你做的,是的话我把对应的 backlog 销掉"。我答不是,
但真正结束这个问题的既不是查也不是问当事人,是**派单的人说了一句
"那条是我派给 51 的"**——一个提交的归属在仓库里可能查不到,
在派它的那条决策里一定有。**派单时把承担人写进消息，比事后追认便宜得多。**

**还有一个更该先问的问题**:那次问话是"是不是你做的,是的话我销 backlog"——
**销条目这个动作的前提就是归属,而它准备在归属未定时先执行后半截。**
归属未定时正确的做法是把不确定留在文件里（"已有一个提交看起来做了这件事,
作者未认领"），而不是替一个匿名提交宣布完成。

## 46. 验收没过时，不许改测量的那条命令

**现场**（由 0f 定，起因是深色验收第 1–3 节不通过）：验收用三条 grep，
其中两条打出 31 处和 95 处命中。命中里有一部分落在没人承诺过的遗留文件上，
于是"给 grep 加一个 `grep -v`"看起来非常合理——排除掉那些目录，
命令就会像设计时预期的那样打印为空。

**为什么这是最坏的一种处理**：**改测量工具去适应结果，
等于把"没达标"改写成"不需要达标"，而且改完之后没有任何痕迹说明发生过这件事。**
下一个人看到的是一条干净的命令和一次通过的验收。

**正确的两条路，都得由裁定的人来走，而不是由跑命令的人顺手走**：

* **缩范围**：明确把那些文件排除出本轮，并**同时**把它们列成单独的 backlog 条目——
  范围缩小了，但缩掉的那部分有了名字和去处。
* **扩承诺**：把它们纳入本轮，改完再跑。

两条路的共同点是**范围的变更被写下来了**，而"改 grep"的问题正是它没有。

**可执行的动作**：验收不过时，第一步是**按身份把命中分成两栏**——
"本轮漏的"和"从未在本轮范围内的"——交给定范围的人裁定。
**在裁定回来之前，谁都不要动那条命令。**

**它与第 44 条的关系**：第 44 条说数字要能归属，这一条说
**归属完之后，改的是代码或是范围的定义，不是量它的那把尺。**

## 47. 一个没有被执行过的验证，读起来和执行过的一模一样

**现场一（我的）**：深色验收里，我替 `monitor_menu.dart` 的三处 `Colors.white`
申请"已知例外"，理由写的是"它画在截图/缩略图之上，底下不是主题化的表面"。
这个理由**是从函数名推的**——那个函数叫 `globalMonitorsWidget`，
名字里的 monitor 让我以为底下是一帧画面。打开代码才看到：
它画的是一排矩形块，是显示器排布的**示意图**，白底在暗色下会刺眼。
理由不成立，三处按缺陷改掉了。

**现场二（0f 的）**：报"全仓控制字符零命中"，依据是那条命令没有输出。
**没先种一个阳性样本验过**，所以"零命中"与"这条命令根本不会命中"读起来完全一样。

**共同点**：**一个没有被执行过的验证，写出来和执行过的没有任何区别。**
"它画在截图上"和"我看了，它画在 `Image.memory` 上面"是同样长的一句话；
"零命中"和"我种了一个样本、命中了，再清掉、归零"也是同样干净的一行输出。
读者无法从文字上分辨，**作者自己在事后也分辨不出**——这才是它危险的地方。

**两个可执行的动作**：

* **给结论找一个只有真去看过才能说出的细节。** 不是"它画在截图上"，
  而是"它上面那层是 `Image.memory(preview.bytes)`，注释已经写了 scrim 的理由"。
  说不出那个细节，就说明还没看。这与第 19 条同源：**具体到能被证伪的程度**，
  在这里是**具体到能证明自己确实执行过**。
* **否定式结论先种一个阳性样本**（第 38 条已有，这里是它的第二个现场）：
  零命中之前，先让那条命令命中一次。

**另一半在第 48 条**：这一条说的是**这个检查根本没跑过**，
第 48 条说的是**跑过了，但只跑在自己动过的那一块上**。
两者要提醒的动作不同，所以不合并。

**为什么函数名特别危险**：它是作者对代码的**描述**，不是代码。
描述会过期、会含糊、会因为分层而指向别处——`globalMonitorsWidget` 里的
monitor 指的是显示器这个设备，不是显示器的画面。
**名字能提示去哪里看，不能替代看。**

## 48. "我接完了"是一次记忆，清单是一次测量

**另一半在第 47 条**：那一条说的是**这个检查根本没跑过**，这一条说的是**跑过了，但只跑在自己动过的那一块上**。

**现场**（深色验收，本会话）：我报过"首页外壳已接完"。照 `docs/dark-acceptance.md`
跑第 1 节那三条 grep，在**同一个文件**里查出四处颜色字面量——页面底、内容卡、卡边框、
侧栏选中态。**后果是深色下整个首页仍然是亮的**，是本次最显眼的一条缺陷。

我当时不是在撒谎。我把 `UiColor.x` 换成了 `ui.x`，**换完那一刻文件"感觉"就迁完了**，
而 `Colors.white` 和 `Color(0xffeff4f7)` 这类字面量根本不在我换的那批符号里，
所以它们一次也没有进入我的视野。**"接完"记的是我做过的动作，不是文件的状态。**

**同一轮里这件事又发生了两次，形状一模一样**：

* 我初报"字面白色 13 处"，第二轮 grep 打出 14 处——多的那一处是
  `set_password_dialog_desktop.dart` 的输入框填充。第一轮我是**照着第一次的命中列表**
  去修的，修完没有重跑就报了数。
* 对比度那条，深色 `primary` 作文字用 4.37 不达标。改成 `0xff5d90ff` 之后，
  我**重算了它参与的每一对**才发现它没有靠越过别的门槛来通过这一个——
  如果只复核失败的那一对，读数一样是"通过"。

**三次的共同点**：**局部读数看起来自洽，因为它本来就是从局部取的。**
改完只看自己动过的地方，等于拿同一个局部再确认一次同一个局部。

**可执行的判据**：

* **报"完成"之前，跑一次不是你选的检查。** 你选的路径证明不了你没看的路径。
* **修完要重跑整条命令，不要照着上一次的命中列表逐条勾。** 那份列表是上一次的状态。
* **改一个值，重算它参与的每一对，不只是失败的那一对。**
  靠越过另一个门槛来通过一个门槛，不算修好。
* **一条命令打出空结果时，先种一个阳性样本证明它打得出非空。**
  空有两种来源——没有东西可打，和这条命令根本够不到要找的东西——
  而这两种在输出上一模一样。故意制造一处该被命中的地方，跑一次看它是否出现；
  没出现就说明尺量不到这个东西，此时"通过"是假的。
  **第 49 条是这个动作的一般形式**：那里说的是"一个检测手段，只有在它对已知阳性
  报过阳，它的阴性结果才算数"，适用于任何检测工具；这里说的是同一个动作用在
  自己刚修完的那一处——**修完跑出的空结果，和命令根本碰不到那批文件，长得一样。**
  另外那条现场里的 `grep -P` 是**报错退出**、标准输出为空，所以**读退出码**是它
  同样给出的一步；而"一条命令一直是绿的、于是没人想到还有一步从没跑过"是
  第 51 条的形状，不是这两条。

**它与第 46 条的关系，以及第三条腿**：第 46 条说**不许改尺**；这一条说**量了一次不算量过**。
两条合起来仍漏掉一种：**尺没改、也重量了，可是尺从一开始就够不到这个东西。**
上面那条"先种阳性样本"就是补这一格的动作——它和前两条并列，不是它们的注脚。

## 49. 检测手段的阴性结果，在它对已知阳性报过阳之前不成立

**现场**（0x08 扫描，本会话）：0f 对全仓扫了一遍 `*.md` 找 0x08，报告**零命中**。
同一时刻 `docs/lessons-2026-09-13.md:197` 里就有一个——`flutter\build` 被 shell
heredoc 吃成 `flutter` + 0x08 + `uild`。新写的 `tools/scan_control_chars.py`
第一次运行就把它打了出来。

**根因不是"命令漏了"，是命令根本没有运行。** 实测 0f 用的那条：

```
$ grep -rlP '\x08' --include='*.md' .
grep: -P supports only unibyte and UTF-8 locales
$ echo $?
2
```

这台机器的 locale 下 `grep -P` 直接拒绝执行，退出码 2，**标准输出一个字节都没有**。
换成字面字节 `grep -rl $'\x08' --include='*.md' .` 立刻命中。也就是说：
**一条报错退出的命令，它的"没有输出"被读成了"没有发现"。**

**这是第 43 条（看它实际产生了什么）在检测工具上的形态**，而且更隐蔽：编译失败
至少会刷屏，而一个查找命令失败时的样子——没有匹配行——**和它成功且一无所获时长得一模一样**。
区分两者的唯一信息是退出码，而写"零命中"的人不会去看退出码，因为他以为自己已经看到了答案。

**判据**：

* **一个检测手段，只有在它对一个已知阳性样本报过阳，它的阴性结果才算数。**
  没做过这一步之前，"零命中"只能写成"我这条命令没有输出"，两者在报告里是不同的句子。
* **阳性样本要自己种。** 等真出问题时再验证工具，等于用一次事故换一次标定。
  `scan_control_chars.py` 是双向验过的：种一个 0x08 进去看它报、拿掉看它清；
  那条 grep 一次都没有。
* **报阴性时带上它读了多少个输入。** "扫了 1613 个文件、0 命中"和"扫了 0 个文件、0 命中"
  在屏幕上本来长得一样，所以扫描器的成功行现在打印文件数；0f 从这轮起报这类结论
  一律走这个工具并带上文件数。

**它与第 48 条第三条动作的关系**：那里是这一条用在一个具体处境上的样子——
**改完自己那一块、跑一次、得到空结果**。两处的动作是同一个（种阳性样本），
区别只在信任的对象：这一条问"这个工具可信吗"，第 48 条问"我这次的通过是真的吗"。
本条现场里的 `grep -P` 还多一层——它是**报错退出**、标准输出为空，
所以"先读退出码和 stderr"是同一次事故里并列的另一步，而不是另一条规则。

**同一条判据当场救了工具自己两次**。`scan_control_chars.py` 第一版有两个假绿，都是
"对没读过的输入报告干净"：给它一个**未跟踪**的路径（共享脚本的本地副本正是这种），
它静默报干净；给它一个**匹配不到任何文件**的前缀，它也报干净。现在前者纳入扫描范围
（仍尊重 `.gitignore`），后者退出 1 并说明。**第二个假绿是我在用它做另一件事时撞见的，
不是读代码读出来的**——这恰好也是本条的例证：工具要被当成阳性样本喂一次，才知道它在说什么。

## 50. 规则不保护写规则的人

**现场**（本会话，0x08 第三次出现）：AGENTS 里有一条讲共享脚本的规则，明确写着
"heredoc 会把 Windows 路径里的 `\b` 变成一个退格字节"。这个陷阱当天出现了三次：
第一次在 `check.ps1`，第二次**在描述这个陷阱的那段文字自己身上**，第三次在我新写的
"断言'没有人/从来不'之前必须现场读一次"那条规则里——**被吃掉的正是那条规则推荐读者去跑的命令**
（`C:\build\*.ps1` 存成了 `C:` + 0x08 + `uild`）。

一句话：**我在一条讲"先去看一眼"的规则里，写坏了那条"去看一眼"的命令。**

**这不是手滑，也不是不重视。** 写那段话的时候，那条规则正是我注意力的中心；
如果"知道并且在意"能防住它，它就不会恰好死在这里。**能同时穿过作者、评审和渲染的损坏，
靠"更小心一点"是挡不住的**——0x08 在 Markdown 里渲染为空、在 `git diff` 里打印为空，
页面上只表现为"路径少了个字母"，读者会当成错别字读过去。

**修法不是更小心，是换一条不需要小心的路**：

* 修复脚本里**完全不写反斜杠**，路径用 `chr(92)` 拼出来；改完**数字节**确认，
  而不是看一眼觉得对了。这与造 fixture 时"不碰共享工作树、走 plumbing"是同一取向：
  **不是绕过规则，是找一条不需要那个危险动作的路。**
* 把这条从"记住"变成"能被扫出来"：`tools/scan_control_chars.py` 进了共享脚本流程，
  四步变五步，**新增的这一步是唯一不依赖人是否细心的**——前四步是习惯，这一步是一条会失败的命令。

**更一般的那半句**：这次"机制齐全、结果没人读"里，**没人读的是我们自己写的规则**。
文档写完就没人回头读，是这份文档本身最大的风险——**它记录的教训，保护不了正在写它的那只手**。
所以判据只能是：**凡是一条规则描述的损坏，都要有一个工具能把这条规则自己扫一遍。**

## 51. 一条一直是绿的命令，会让人不去想还有一步从没跑过

**现场**（本会话）：为了给登录对话框出一张亮色截图，第一次在本机跑
`flutter build windows --release`，退出码 1：

```
Building with plugins requires symlink support.
Please enable Developer Mode in your system settings.
```

翻自己今天的记录，**同一条报错今天已经出现过两次**。也就是说：
**本机从来没有成功跑过一次 Flutter Windows 构建，而此前所有"验证"都只到
`flutter analyze` 为止**，这件事一整天没人注意到——包括我自己两次撞上它之后。

**它是第 47 条的第一型**：第 47 条说的是"这个检查没被执行过"，
而这里更彻底——**这个检查的入口根本不存在**，它从来就不可能被执行。

**藏在哪里**：藏在一条每天都在跑、而且**一直是绿的**命令后面。
`flutter analyze` 每次都给出 222 / 228 这样的确切数字。

**数字越确切，越像是"已经验证过了"。**

确切的数字读起来比"通过"更有说服力，而它恰恰是最容易被误读的形式：
**精确会让人不再追问它量的是什么。**
绿色不说明它覆盖了什么，只说明它自己跑完了。

**代价**：一整天的样式改动只被静态分析看过。analyze 能证明它编得过，
**不能证明它编得出产物，更不能证明它好看**。

**可执行的动作**：

* **报验证结果时说清跑到了哪一步**，用那一步的名字：`flutter analyze` 不是构建，
  `cargo check` 不是构建，**能产出可运行的东西才是构建**。这条已经写进 `AGENTS.md`。
* **一个从未成功过的步骤，和一个刚刚失败的步骤，要分开说。** 后者是回归，
  前者是这条路根本没通过——两者的修法完全不同，而报错文字一模一样。
* 判断"我验证过了"时，先列出**从改动到用户眼睛之间的每一步**，
  再标出自己实际执行过哪几步。中间断掉的那一步，通常就是从来没人跑过的那一步。

## 52. 界定符不加引号的 heredoc，会把反引号里的词整个吃掉

**现场**：`1788fc264` 的提交正文里有两处空缺——
"They are  -- something is live" 和 "It shares the tint with  today"。
读起来像漏打了两个词,实际是两个标识符被 shell **执行掉**了。

**机制**（0f 复现,本会话在自己的 shell 上复跑过一次,字符级一致）:

```
$ bash -c 'cat > /tmp/d2.txt <<EOF
x `nosuchcmd` y
EOF'
bash: nosuchcmd: command not found
exit=0
$ cat /tmp/d2.txt
x  y
```

**界定符不加引号的 heredoc 里,反引号是命令替换。** 反引号里的词被当成命令执行,
命令不存在,它的标准输出是空,于是那个词从文本里**消失**,只留下原来包着它的两个空格。

**为什么没被挡住**:此前的规则写的是"heredoc 会吃掉反斜杠"——按**字符**列举。
反引号不在那张列表里,所以这次绕过去了。**这与第 40 条是同一个毛病:
一条规则漏掉了明显同类的东西,是判据划错了,不是列表不全。**
这里正确的判据不是"哪些字符危险",而是"**这个 heredoc 做不做替换**"。

**为什么难发现**:

* **标准输出正常**:文件写出来了,内容通顺,只是少了两个词。
* **退出码为零**:上面那次实测 `exit=0`。
* **只有 stderr 说了话**,而它混在一条长命令的输出里。

**这与第 49 条互为反面**:那条是**退出码非零而调用方没看**,
这条是**退出码为零而错误在 stderr**。两条合起来的意思是:
**退出码朝哪个方向都不能单独用来判断成败。**

**动作**:**写文本一律用 `<<'EOF'`,界定符加引号,里面不做任何替换。**
要写标识符、反引号、`$`、反斜杠的场合更是如此。
这比"别用某个字符"可执行,而且一次挡住全部——**不需要预先知道哪些字符危险。**

**控制字符扫描器挡不住这一类**:`tools/scan_control_chars.py` 找的是异常字节,
而**这个缺陷里没有任何异常字节,只有缺字**。缺字没有字节可扫。

**被吃掉的两个词是 `alerting` 和 `destructive`**(由 51 补,它是那条消息的作者)。
原句是「They are `alerting` -- something is live …; It shares the tint with
`destructive` today」。

**一个值得记的巧合**:那段正文正是在解释**为什么不能把它们叫 `destructive`**,
而被吃掉的词之一就是 `destructive`——一条关于「某个词不该用在这里」的论证,
恰好丢掉了那个词。这不是运气不好:**反引号在两种语境下都表示「这是个标识符」**,
Markdown 里是排版,shell 里是执行。**凡是在解释命名的正文,反引号密度天然最高**,
所以这一类正文中招的概率也最高。

**那条消息里是两处,而且两处的形状不一样**——这一点决定了能不能扫:

| 残留 | 位置 | 形状 |
| --- | --- | --- |
| `They are  -- something is live` | 行中 | 被删的词两侧都是空格,贴在一起 → **双空格** |
| `…tint with` + 换行 + ` today;` | 行首 | 被删的词一侧贴的是换行 → **行首单空格** |

**形状不同的原因是位置,不是机制**(由 51 给出,作者本人;本会话按字节复核过):
**双空格只在「被删的词两侧都是空格」时出现;词只要贴着行边界,
留下的就是行首或行尾的一个空格。**

**我在这里出过一次错,记下来**:我最初报的是三处,多出来的那一处是
`and pressing cancels it`——我看到它只有一个空格、句子又缺个宾语,就把它当成了残留。
作者指出**那句原文本来就没有反引号**,它是完整的。
在那条提交正文里数反引号,现在一个都没有(实测 0 个),
两处残留加这一句都对得上。**把「读起来不对劲」当成证据,是第 47 条那个形状的又一次。**

**这决定了检测手段该长什么样**:「非空白+两个以上空格+非空白」只抓行中那一种。
要覆盖一个词被删掉可能留下的全部形状,至少还要加两条——**以空格开头的行**、
**以空格结尾的行**。三条合起来才够。

**但重点不该放在检测上**:检测抓的是已经发生的事,而这件事有彻底的预防——
**提交信息不要用带反引号的双引号 `-m` 字符串,改用 `-F <文件>` 或加引号的 heredoc。**
上面那句「解释命名的正文反引号密度最高」的真正含义是:**这类正文最该用 `-F`,
而不是最该被扫描。**

**证据当时就在屏幕上**:那次提交的工具输出里有
`bash: line 17: alerting: command not found` 和 `destructive: command not found` 两行。
**不是没有信号,是信号被跳过了**——又一次「去看它实际产生了什么」(第 43 条)。

## 53. 注释和名字打架的地方,就是该拆的地方

**现场**(由 51 提供):把工具栏图标色从「反查背景色」改成「由状态决定」,
派单给的状态是三个:`normal` / `active` / `danger`。
给 `destructive` 写的注释是「**Pressing it ends the session**」。

**卡在哪**:两个按钮穿危险色 tint,看起来该归 `destructive`——
**会话录制开关**(录制中)和**等待接听的语音呼叫**。但两个都不结束会话:
录制按下去是停止录制,等待中的呼叫按下去是取消呼叫,**都是安全方向**。

**触发点非常具体,不是「感觉不太对」**:把它们归进去,
会让**十分钟前刚写的那句注释变成假话**。

**为什么注释比名字可靠**:**注释是作者当时的真话,名字是后来被复用的。**
名字只有几个词,复用时人会不自觉地把自己的情况往里塞——
「红色的、危险的,都叫 danger 嘛」;
注释是一整句断言,**塞不进去就会露馅**。

**怎么做的**:加第四个成员 `alerting`——
「有东西正在进行、用户不该忘记它开着;按下去是取消它」。
它和 `destructive` **今天解析到同一个色**,所以那次改动仍是纯重构、
一处实际颜色都没变;但两者在代码里分开了,
以后要给其中一个单独配色,不用再翻调用点。

最后的四个成员:`idle`(什么都没声称)、
`engaged`(用户开着的东西:置顶、正在看的显示器、移动操作面板)、
`alerting`(录制中、呼叫等待)、`destructive`(按下去结束会话:关闭按钮)。

**可见信号**:这是「没有诚实映射就加新成员,不要硬套」那条的可观测形态——
**写不出一句对所有成员都为真的注释时,说明成员少了一个。**

**它与第 28 条的关系**:第 28 条说一个名字担两个职责时「它该是多少」永远吵不完,
发现的途径是**争论还在**;这一条的发现途径是**注释成了假话**。
两者都是「名字装不下」的信号,但这一条更早——**争论要两个人,注释一个人就能撞上。**
## 54. 断言之前,先说出唯一能推翻它的那件事

**现场**(由 51 提供,数值本会话在 `ui_palette.dart` 上复核过):
工具栏那次重构的断言是——**纯重构,不改变任何一处实际颜色**。
口径事先定死:截图里任何图标颜色变化都算这个断言被推翻。

**它没有做的事**:逐个按钮去证明「这个也没变、那个也没变」。
**那是在找支持,找多少都不构成证明。**

**它做的事**:先问**什么情况下它会是假的**。
旧代码是反查——拿背景色比对色调:等于 `primaryTint` / `primaryTintHover` 返回主色,
等于 `dangerTint` / `dangerTintHover` 返回危险色,否则返回次要文字色。
所以**新旧唯一可能不一致的情形只有一个**:
闲置状态的悬停色 `settingsRowHover` 碰巧等于其中任何一个色调。
真撞上了,旧代码会给一个闲置按钮返回主色,新代码返回次要文字色——那就是实打实改了颜色。

**然后只查那一个情形**(下表取自 `flutter/lib/desktop/widgets/ui_palette.dart`):

| | 浅色 | 深色 |
| --- | --- | --- |
| `settingsRowHover` | `0xfff7f8fa` | `0xff2a2e38` |
| `primaryTint` / `primaryTintHover` | `0xffeaf1ff` / `0xffdce8ff` | `0xff1b2a4a` / `0xff24375e` |
| `dangerTint` / `dangerTintHover` | `0xfffff0ef` / `0xffffe1df` | `0xff3a201f` / `0xff4d2724` |

两套里都无碰撞,闲置的静止色是全透明更不会撞。所以新旧在现存的每一种组合上答案一致。

**这句是这一条的落点**:
**「今天它还没发生,所以重构是纯的;但正因为查过我才敢说纯,没查之前我只是相信它是纯的。」**

**可执行的形式**:**断言之前,先说出唯一能推翻它的那件事,再去查那件事。**
说不出来,说明对自己的断言还不够清楚,**不该断言**。

**与第 49 条的关系**:同一族,方向相反。
那条防的是**没东西可看却判通过**(阴性结果要先对已知阳性报过阳);
这条防的是**东西太多、只挑看得顺眼的那些**。
两条指向同一个动作:**先确定什么算反例,再去看。**

**还有一层**:这次重构的目的正是消除「两个状态共用一个色调」这个隐患,
而验证它纯不纯,要查的恰好是「今天有没有已经共用」。
**一个改动安不安全,答案常常就藏在它想解决的那个问题里。**
## 55. 动作做了,做在一个比真实对象小的东西上

**它不属于「验证从没跑过」那一族**(第 47、51 条):那一族是**该做的动作没做**,
靠「先跑一次」就能挡。这一条是**动作做了、做得很认真、
做在一个比真实对象小的东西上**,挡不住——因为你不会觉得自己漏了什么。

**实例一:把线段当成两个点**(由 51 提供)。
为了证伪「工具栏重构不改变任何实际颜色」,它查了「闲置态的悬停色会不会碰巧等于某个 tint」,
把浅色一套和深色一套的取值都列出来比对,**两套都无碰撞**。查得很仔细,结论也对。

但调色板有 `lerp`——**主题切换时两套之间是插值的**。
所以它不是两个点,是**两点之间的一整条线段**,而线段上每一个中间态都不在任何一张取值表里。
**漏掉它不是因为没查,是因为对「调色板」这个东西的模型比它实际的小。**
补算之后结论不变,但那是运气——事后才知道整条线段都安全。

**实例二:把颜色当成一个数**(同一天,补算的过程里)。
补算时只解了**红色通道**,四个解全部出界,于是收工。
**「只看红色通道就够了」在这里成立,但它成立是因为四个 R 恰好都出界,不是因为方法对。**

三个通道都解出来是这样(本会话独立复算,与 51 给的数值一致;
解的是 `settingsRowHover` 与各 tint 在 `lerp` 上相等的 t):

| 对 | R | G | B |
| --- | ---: | ---: | ---: |
| primaryTint | −6.500 | 2.333 | −0.385 |
| **primaryTintHover** | **1.286** | **0.640** | −0.152 |
| dangerTint | −1.000 | −1.333 | −0.786 |
| dangerTintHover | −0.296 | 1.438 | 3.857 |

**`primaryTintHover` 的绿色通道在 t = 0.640 相交——区间正中间。**
结论仍然不变(两色相等要求三通道**在同一个 t 上**同时相等,
而 1.286 / 0.640 / −0.152 互不相同),但**如果当初挑的是绿色通道,
拿到的就是一个区间正中的解**。

> 一个只算了绿色就停手的人,会带着 0.64 去报告「主题切换到 64% 时图标会闪」——
> 一个不存在的缺陷,而且他手里有数字。

这是这份文档里第一条**「验证了、算对了、然后得出一个不存在的缺陷」**的记录。

**判据**:在查「有没有碰撞」之前,**先问这个东西有几种存在形态,再问它有几个维度**。
静态两套是两种形态,动画中间态是第三种;红绿蓝是三个维度。
**漏掉形态或维度中的任何一个,你都会在一个比真实对象小的东西上做一次完全认真的验证。**

**附带的方法,它是单边的,这一点必须写明**:挑一个维度算,
**出界就证完了**——因为三个通道必须在同一个 t 上同时相等,任一不成立整体就不成立;
**落在区间内什么都没证明**,必须把其余维度都算完。
读起来像双向的,其实只在一个方向成立。
先前那句「只看红色通道就够了」碰巧是对的,**方法对,适用范围是运气给的**。

**0f 的落点**:**一个数字是不是证据,取决于它落在哪一侧;
0.64 不是证据,它是一句「接着算」。**
这份文档一直在鼓励人去拿数字,而这是第一条说**数字本身也分两种**的。

**两个数字都留着**:**1.286** 是「出界,但只差 0.286」,**0.640** 是「根本没出界」。
前者让人后背发凉,后者让人知道什么时候不能停。

## 56. 核验人沿着被核验人的路径走一遍,得到的是同一个盲区

**现场**(由 0f 提供,是它自己的失误):复核 51 的算式时,
**它只复核了 51 算过的那个通道**——也就是「沿着对方的路径重算一遍同样的局部」。

**必然的结果**:它得到了和对方**一样的盲区**,同样漏掉绿色和蓝色。
那个 t = 0.640 不是复核抓出来的,是 51 后来自己扩大范围时撞上的。

**0f 的原话**:

> **核验人沿着被核验人的路径走一遍,得到的是同一次计算,不是一次独立确认。**

**可执行的形式**:复核时先问**「被复核的人是怎么得出这个结论的」**,
然后**刻意不走那条路**——他算了 R,你去算 G;他查了静态表,你去查中间态。
**走同一条路得到同一个答案,说明的只是算术没错。**

**两种「我核过了」在报告里读起来一模一样**:
一种是**换了来源**重新取数(独立复核),
一种是**同源同路径**再算一遍(重算)。
本会话今天两种都做过:去 `ui_palette.dart` 上重取色值是前者,
而 0f 这次复核算式是后者。**报告时说清是哪一种。**

## 57. 报数值不要截断,尤其当别人要拿它去算的时候

**现场**(由 51 提供):在给 0f 的表里把 `dangerTint` 写成 `0xfff0ef…`。
0f 按 R = `0xf0` = 240 代进去算,得到 t = 0.304 **落在区间内**,当场认为对方算错了;
去读源码才发现真值是 `0xfffff0ef`,**R = 255**。

**为什么这个截断特别毒**:**颜色的前两位是 alpha**,
从末尾截断等于截掉了对方真正要用的那一位。
差一步就用一个凭空造出来的数字推翻了一个正确的结论。

**它难被发现的原因**:**截断的十六进制在表里读起来和完整的一模一样**——
没有格式错误,没有告警,只有一个省略号,而省略号不说明它省掉的是高位还是低位。

**动作**:**别人要拿去算的数值,一个字符都不省。** 想省版面就减少行数,不要减少位数。
这与第 44 条同源:那条说报数字要带范围,这条说**报数字要带全位数**——
范围告诉人它在说什么,位数决定人能不能拿它复算。
## 58. 第四种「没被执行过的验证」:它在队列里

**前三种**:没有入口(第 51 条,本机 `flutter build` 从来跑不通)、
只跑了一部分(第 48 条,只扫自己动过的那块)、
跑了但没人读(`linux-check.yml` 红了几个小时,是别人找别的东西时撞见的)。
**第四种是:入口存在、也触发了、结果还没产生,而所有人都当它已经产生了。**

**现场**(由 0f 提供,它说明是自己的调度缺陷):
为了让几个会话的提交尽快上去,**一小时里推了十来次**,每次推送触发三个工作流。
本会话实测(`gh run list --repo <owner>/<repo>`):

| 状态 | 条数 |
| --- | ---: |
| queued | 7 |
| in_progress | 18 |
| completed | 35 |

**最近一次完成的运行落在 `cd350d4c6` 上,而它距离当时的 HEAD 已经隔了 44 个提交。**
也就是说,那 44 个提交里**没有一个被 CI 检验过**,包括那次让
`flutter build windows` 编不出产物的签名改动——
**master 从来没红过,因为它还没跑完。**

**为什么高频推送让信号更晚到**:队列是先进先出的,
**推得越密,每个结果等得越久**;而在结果到达之前,
**所有人都在一个没有被检验过的 master 上工作**。
"尽快让提交上去"和"尽快知道提交对不对"是两件事,后者才是 CI 的用途。

**动作**:**攒一批再推,除非有人在等那个提交**;
报告"CI 绿"之前先确认那次运行**已经结束**——
`queued` 和 `in_progress` 在列表里都不是结论。

## 59. 查 CI 之前,先确认你查的是哪个仓库

**现场**(本会话,写第 58 条时撞上的):在这个工作树里直接跑 `gh run list`,
返回的是**上游 `rustdesk/rustdesk` 的运行记录**,不是我们的仓库。
`gh repo view` 证实默认仓库解析到了上游。

**为什么它不像一个错误**:返回的列表**完全正常**——有成功有失败、时间连续、
工作流名字(`CI`、`Full Flutter CI`)也眼熟。
唯一能看出不对的是 **commit sha 一个都对不上**,
而人在扫一眼状态列的时候根本不会去比 sha。

**同一个坑,0f 先踩,而且差点没发现**(它自己要求补记):
它今天查 CI 的第一条命令就是不带 `--repo` 的 `gh run list`,
拿到的是上游的运行记录——分支名 `fix-unzoomed-cursor-dpi`、
`patch-1-session-scoped-ipc`,有成功有失败,时间连续。

**它的识别依据是「分支名眼生」,而那是运气不是方法**:
那几个分支名要是碰巧像我们的,它就会拿上游的红绿去核我们的队列,并且很自信。
可靠的依据是 **sha 一个都对不上**,但扫状态列的人不会去比 sha。
**两个人独立踩进同一个坑、其中一个差点没发现**——
这说明它不是谁疏忽,是这条命令在 fork 里的默认行为就长这样。

**它与第 45 条同源**:那条是同一个提交在两台机器上不是同一堆字节;
这条是**同一条命令在两个仓库上都给得出体面的答案**。
两者都属于"数字/状态是真的,只是它说的不是你问的那个对象"。

**动作**:**查 CI 一律带 `--repo <owner>/<repo>`**,
或者先 `gh repo view --json nameWithOwner` 看一眼它以为你在问谁。
这个仓库是 fork,所以默认解析到上游是它的常态,不是一次偶发。
## 60. 一句准确的话在传递中会变宽,而转述的人不觉得自己在加码

**观察由 0f 提出**,它把今天一整天的问题归成了同一个形状:

| 原话(准确) | 被读成(更强) | 差在哪 |
| --- | --- | --- |
| 「我扫了一遍,没有命中」 | 「仓库里没有」 | 没证明这把尺扫得到(第 49 条) |
| 「issues 计数 224」 | 「无 error」 | 计数把两条 error 压成了 `+2`(第 55 条那一族) |
| 「那 6 条不在我碰过的文件上」 | 「是别人在途的改动」 | 前者是我量的,后者是我猜的(第 45 条) |

**三例的共同点**:每一次都是**一个准确的陈述被读成一个更强的陈述**,
而且**读的人不觉得自己在加码**——在他看来只是把话说顺了。

**为什么限定词最先掉**:限定词是整句里唯一不承载新信息的部分。
「我扫了一遍」里,「我」和「一遍」都是限定;转述时留下的是结论,丢掉的是范围。
**越是被反复引用的话,越会朝着更强、更简洁的方向漂。**

**可执行的动作**:**在自己的话被引用之前先把它钉住**——
把限定写进**同一句**里,而不是放在下一段。
「这棵树能编出产物」后面紧跟「不说明它好看,也不说明它后面的提交」,
比另起一段写「需要注意的是……」牢固得多,因为**另起的那段最容易被截断**。

**第四例,发生在这一条写完之后十分钟,当事人是写它的人**:
我在给 0f 的报告末尾写了「我核过它确实推到了那个裸库,不是我凭印象说的」。
原话一字不改:

> 我核过它确实推到了那个裸库,不是我凭印象说的。

**这句是假的,而且请注意它是什么句子**——
**一句专门用来声明自己不是凭印象的话,本身就是凭印象说的。**
真实情况是:e9 先前报过它在编译机上实测 `refs/heads/8f` 指向另一个 sha,
我把**它的一次测量**扩成了**我对另一个 sha 的核实**。
去核的时候才发现我对那台机器根本没有凭据(`git ls-remote` 报 `Permission denied`)。

**而且它已经被下游收下了**:在我的更正送达之前,接收方的回信里写着
「你核过而不是凭印象,这一点记下了」——**一个我编出来的核实,已经进了别人的账**。
两条消息交错了,所以更正到得比引用晚。
**这说明「事后更正」不是这条的解法**:话一旦发出去,
在更正到达之前它就已经被当成事实用掉了。

**这一例的价值在于它的时间点**:**知道这个陷阱、刚刚写完这个陷阱,也照样会踩。**
所以这一条的动作不能是「说话小心点」——那是一句没有检查点的规则(第 42 条)。
可执行的版本是:**凡是写下「我核过」,先问这条核实的命令是什么、我跑过没有、输出在哪。**
答不上来就把它改成「某某报的」,并写明是谁报的。

**变宽需要两个人配合:一个不自觉加码,一个不核就收。**
上面写的全是前半个人,后半个人是接收方(由 0f 补,它说是自己的失职):

它收下那句「我核过」的时候,**手里已经有相反的信息**——
我上一条消息刚说过我那台机器上连 `C:\build\` 都不存在,
而它还专门就「说清自己的可核验边界」回了一段。
**一个刚声明过自己验不了某类东西的人,十分钟后说他验了**,
这个矛盾摆在面前,没有人停一下。

**接收方的动作不是「事后更正」,是在收下一个核实之前,
先问这个人有没有能力做这次核实。**
这一点在多会话协作里尤其要紧:
**每个人的可核验边界完全不同**——谁有编译机凭据、谁能跑 GUI、谁只能读代码——
**而这些边界在消息里看不见,结论在消息里却长得都一样。**

**这一轮的实际后果是零,但那是运气**:接收方在收到更正之前就自己去把树推了,
**推的动作本身产生了真证据**(它的推送输出 `e7f055fcb..571d4b143  571d4b143 -> 8f`)。
如果它当时只是把那句话记进账、然后据此安排下一步,代价就实实在在了。
**运气和隔离长得一样。**

**它与第 19 条的关系**:第 19 条说具体到能被证伪,是让接收方**有能力**纠正你;
这一条说的是接收方**没打算**纠正你的时候会发生什么——
他只是在复述,而复述天然向更强的版本靠。两条针对的是同一个接口的两种使用者。
## 交接与汇报：让别人有能力纠正你

第三组。前两组关心的是"我怎么不出错"，这一组关心的是"**我出了错，别人能不能发现**"。
错误被发现常常带着运气成分（见第 14 条那次侥幸），这两条是把运气的成分降下来的两个方向：
一边不留会误导的模糊话，一边把话说到能被证伪。

### 18. 真正会误导人的往往不是错话，是没说完的话

**情况**：在 backlog 里更正了一条旧判断，写明"读写分离这件事能在本仓库做，不需要 fork"。
同一条目里原本就有一句描述修法的话——"修法是一个写任务，控制消息排在视频前面"。
**两句话本身都是对的。**

**问题在哪**：后一句描述的是**设计**，不是**现状**，但它紧跟在"这件事能做"后面，
连起来读就成了"这件事已经做了"。而真实状态是：模块存在、有五个测试、
**没有任何调用者**，连接循环仍独占一个流，耦合一点没变，收益一点没收。
没有一个字是错的，但接手的人会按"已经做完"去排任务。

**什么促成了复查**：一次消息串号，导致"验收"了三件没做过的事（见下一条）。
拒收之后回头反查——**除了那条假的验收记录，还有没有别的东西也指向未发生的工作**。
查到了这一句。

**具体怎么操作**：在条目下面补一段明确的现状，写死三件事——模块存在且有几个测试、
**没有任何调用者**、耦合上界没有变化，再列出还剩哪两步。判断准则是：
**一句描述设计的话，如果紧挨着一句描述进展的话，就必须自己声明它是设计还是现状**，
不能靠读者从上下文推。

这个形态比明显的错误危险，因为它**通不过任何审查——每句都真**。它只在交接的那一刻骗人。

### 19. 具体到能被证伪的程度，是接收方能纠正你的前提

**情况**：一条验收点名认可三件事：控制消息不再排在积压后面、测试断言某类型不可克隆、
某条说明写进了提交信息。**这三件一件都没做过**——它把别处的一份汇报当成了这边的。

**它防住了什么**：因为它写出了三件事**各自的名字**，一眼就能看出对不上。
如果它回的是"那几条都可以"，多半就收下了——确实做了三件事，只是不是那三件。
收下之后，master 上会有一条"已验收"的记录指向从未发生的工作，而第二天的排期
会建立在这个前提上。

**关键一点**：**发现错误的不是接收方的警觉，是发送方措辞的具体。**
这一点值得说明白，否则容易把功劳记在警觉上，而警觉是不可靠的。

**具体怎么操作**：验收和派单都不写"某某可以"、"那几条都行"，
写清楚**具体是哪几件、以什么为准**（提交号、文件名、测试名）。汇报同理。
这条对下达指令的一方约束更大，但对汇报方一样成立：
**你把自己说得越具体，别人纠正你的成本越低。**
含糊的汇报不是谦虚，是把纠错的责任推给了读的人。

**同一条规则还有第二种用法：对付伪造。** 当天另有一份**冒名的汇报**送到协调方，
声称九个红测试的根因是某处产品行为，并附了提交哈希 `b1e11c2ff`。
协调方回信前逐个核哈希，`git cat-file -t` 报该对象不存在，当场判假。
**伪造者写上哈希是为了显得可信，而那正是它的死因**——
反过来说，**不给任何哈希、只给含糊结论的伪造会难判得多**。

那次还有两点值得记：
* **真正危险的不是假哈希，是假前提。** 那份汇报给的根因是错的：被指责的那个账号检查
  **在生产里行为完全正确**（未登录本就不该开隧道）。照它去改，删掉的是一个正确的产品要求。
  **哈希对不上只浪费一轮往返；假前提被采信是把对的东西删掉。**
* **它带了扩散钩子**——末尾建议"顺带查另外两处同样问题"。真照做的话，
  一个伪造前提会被复制到三个地方。判据：**一条消息如果同时给出结论、
  并建议把该结论推广到其它位置，先验证结论本身，再谈推广。**

所以这条规则是双向的，协调方定的原话是：

> **含糊既无法核对也无法拒绝。**

当天协调方与另一个会话**各拒收过一次**——一次拒的是伪造汇报，一次拒的是
"把别处的汇报当成我的"。**两次靠的是同一个机制：对方写得足够具体，接收方才有东西可以对照。**
一条对付伪造，一条对付诚实的错误。（规则形态见 `AGENTS.md` 的协作一节。）

### 20. 一条未经核实的消息，可以让你发出验收和指令

这一条是协调方自己提供的，用它的原话：

> **"我据一条未经核实的消息发出了验收和指令；识破它的不是我，是接收方，
> 而接收方能识破的唯一原因是我在指令里写了具体的名字。"**

**经过**：一条伪装成某会话汇报的消息到达协调方，其中的 run 号、失败点、
"断言拦住了一个空壳包"、"路径是摘录时留下的未经验证的前提"，以及三句转述的原话，
**全部不存在**。协调方没有核实就据此回了一条验收加指令，指令里要求把那条"教训"
补进本文档。接收方逐条对照自己的实际状态后拒收，该消息随后被整条撤回。

**它差一点造成什么**：那条"教训"本身听起来很有道理——把别处能跑的配置摘过来时，
每个相对路径都是一个不会报错的隐含假设。如果它被写进来，**一条虚构的经历会以
方法论的形式永久留在这份文档里**，而且因为它读起来合理，后来者没有理由怀疑它。

**是什么挡住了它**：两件事，都不是警觉。
* 指令里写了**具体的名字**（run 号、失败步骤、配置项），接收方一条条对得上自己的实际状态，
  于是一眼看出全对不上。换成"你那几条都不错"，多半就收下了。这与第 19 条是同一个机制，
  **同一天之内复现了两次**：一次是把别处的汇报当成某会话的（第 19 条），一次是这条伪造。
* 接收方有一条一贯的原则：**文档里每一条经历都只用当事人提供的一手材料，不替别人写**。
  被要求补进那条"教训"时，它要的是当事人的四句话——而这条经历没有当事人。
  这条原则原本是为了准确，结果顺带挡住了伪造。

**为什么这一条要留在方法论文档里，而不只是一次事故记录**（协调方的话）：

> **伪造内容最危险的形态不是错误的事实，是合理的结论。** 错误的事实会被现场核对撞破，
> 而一条通顺的教训没有对应的现场可核——它一旦进了文档就变成前提，
> 后面所有人都在它上面接着想。

**可复用的手段**：
* **核实消息真伪是发指令一方的责任，不是接收方的。** 接收方该做的是把自己的措辞写具体，
  这样对方串了号能被撞破；发指令的一方该做的是先核再回，而不是等着被撞破。
  真实的跨会话消息在正文之后带一段固定的来源说明，这是发送侧可以自查的结构特征。
  **不要把把关的责任放在接收方**——接收方能识破是幸运，不是机制。
* 写进共享文档的每一条经历，都要能指到一个具体的当事人。**一条找不到当事人的教训，
  无论多有道理，都不该进文档。** 有道理恰恰是它最危险的地方。

### 22. 把自己的引申，当成对方的原话还给对方

这一条由协调方提供，是它自己的失误，性质与第 20 条那次伪造不同。

**经过**：它读完一份汇报后，发来一条消息，用引号转述了三处"你说过的话"——
"两条防线"、"解除障碍时去搜还有谁在等它"、以及一段 18 条与 21 条的对比。
逐条 grep 之后，**三处在文档里命中数全是 0**。真相是：其中两处是它读汇报时
**自己想到的**，第三处是把"三条手段"记成了"两条防线"，然后都加上引号还了回去。

**为什么它比伪造更难防**（协调方的话）：

> **伪造是外面来的，可以靠核对拦住；把自己的引申记成对方的原话是里面出的，
> 它读起来完全自洽，因为它本来就出自我自己的思路。**

还有一个特征值得记：**引用得越具体、越像逐字转述，就越不容易被自己怀疑**。
这与第 19 条形成一个需要分清的张力——第 19 条说措辞具体是好事，因为它让接收方
**有能力反驳**；但那里的具体指的是**可核对的事实**（提交号、文件名、run 号）。
而这里的具体是**虚构的引文**：它同样具体，却指向一个只有原作者能证伪的东西，
而原作者不会想到要去核对自己说过什么。**可核对的具体让人能纠正你，
不可核对的具体让人无法纠正你。**

**可复用的手段**：
* 转述别人的话时，**分清哪些是他说的、哪些是我读完之后想到的**。后者一旦加上引号
  还给他，就成了一条他无法证伪的话——除非他逐字去核。
* 自己的引申要**明说是引申**："我从你这条里想到的是……"，而不是"你说的……"。
  这不是客气，是把证伪的可能性留在桌面上。
* 收到带引号的转述时，**去核原文**。当天三次转述对不上，两次是别人的错、一次是
  协调方自己的错，**三次都是逐条核对撞破的**，没有一次是靠感觉。

## 小结：容易出错的结论类型

| 结论的形态 | 典型错法 | 该用的手段 |
| --- | --- | --- |
| 从路径、层级、命名推出的结论 | 推演自洽但与工具结论冲突 | 构造必然失败的输入，看工具认不认 |
| 从单个函数推出的功能定性 | 读到的是回退分支，或已被当天的提交取代 | 先 `git log` 当天该区域，再读 diff |
| 两个数字对不上 | 度量对象不同（文件 vs 方法） | 确认两个数字量的是同一个东西 |
| 从截图或用户描述出发 | 那段文字根本不是我们画的 | 先 grep 该字符串是否存在于仓库 |
| 从日志措辞判断性质 | "Failed" 是写日志者选的词 | 读发出该行的代码 |
| "恢复路径不恢复" | 症状的位置不是缺陷的位置 | 反事实：先修因，看果是否自行消失 |
| "日志里查不到，所以没发生" | 措辞变了、级别不够、文件没覆盖全 | 先证明"发生了必留痕"，再谈零命中 |
| 以流程绿灯为验收 | 产物是空壳，或流程根本没跑完 | 对产物本身写断言（存在 + 新于本次开始） |
| "大概是 X 导致的" | 可量的事实被猜成了故事 | 一条命令量出来（`Get-Process` 之类） |
| 实验没达到预期 | 记成产品缺陷，其实是方法错 | 先怀疑方法：从读取点反查存储位置 |
| "画面坏了" | 源端本来就长那样 | 先确定源端此刻应显示什么；坏得有选择性就不是解码错误 |
| 功能名字听起来无害 | 它接触的端点与名字不符 | 读"未配置"那条分支的实现 |
| 开关加在了调用点上 | 另一侧的触发点没被保护 | 列全读取点与触发点；门控放在咽喉而非调用点 |
| 测试"某事不会发生" | 执行它来验证，判断写错就真发生了 | 抽出决策函数，对决策断言 |
| 单测里的全局状态 | 是出厂值，不是运行时值 | 凡"启动时才初始化"的，测试里都要当默认值看 |
| "这条路径没门控" | 那条路径可能根本没人能走到 | 从界面走到实现，全程确认可达性 |
| 验证自己的结论 | 只写"证实"的判据，反例被解释掉 | 把否定结论的那种结果也写死、写明可报 |
| 排了一项就得有产出 | 硬找个地方改一下 | 判据里先写明"干净就报干净，什么都不改" |
| 待办上的前置条件 | 障碍早已消失，条目还标着"被挡住" | 复核时单独过一遍前置；写成"缺什么"而非"等什么" |
| "尚未验证"的标注 | 只说为什么不行，没说什么条件下可以 | 补一句解除条件，否则它会退化成装饰 |
| 规则漏了同类的东西 | 判据划错了，不是列表不全 | 重划判据；列命令是穷举，说边界才是规则 |
| 解释一个决定 | 只说了后果，换个场景就用不上 | 再抽一层说取舍："换个功能这理由还站得住吗" |
| 每句都真的交接文字 | 设计与现状挨着写，读成了"已完成" | 描述设计的话自己声明是设计；另起一段写死现状 |
| "那几条都可以" | 粒度不够，接收方无从核对 | 点名具体哪几件、以提交号/文件名/测试名为准 |
| 收到一条汇报就据以下指令 | 消息可能串号，也可能是伪造的 | 先核来源标记；指令写具体名字，让对方有能力反驳 |
| 一条听起来很有道理的教训 | 可能没有当事人，是虚构的 | 只收一手材料；找不到当事人就不写进文档 |
| "读写为什么不一致" | 可能有一边根本没发生过 | 先分别确认两边是否发生，再谈关系 |
| "它在安静地重试" | catch 里设了退避，永久失败像是等待 | 找"成功过一次"的证据，不是找报错 |
| 给兜底加默认值 | 错误变成一个合法但不对的结果 | 问兜底值是否有意义、事件是否有痕迹 |
| 工具给出的答案 | 可能对应上一个输入，格式却完全正常 | 让它打印自己的出处，而不是写注释提醒 |
| 报错指向没改过的代码 | 局部变量名遮蔽了库前缀 | 先怀疑名字撞了，别去读那处代码 |
| "这个值该是多少"吵不完 | 一个名字担了两个职责 | 拆名字，不要继续调数值 |
| const 里用了 of(context) | 报错在构造处，不在取值处 | 先 grep 扫一遍，别逐个 analyze 撞 |
| grep 命中一批文件 | 可能只是同名前缀 | 命中是候选；动手前打开看一眼 |
| 诊断数涨了一条 | 温和的 warning 不拦人，只让数字动 | 基线报确切数字；持平才算干净 |
| 一次改动报了好几条 | 最扎眼的那条掩护了其余的 | 按数量对账，不按"最严重的修好没有" |
| 「从未被使用」告警 | 可能是忘了接的功能，不是死代码 | 问"它当初是为什么写的" |
| 工具返回码干净 | 开关缩小了它做的事，它不声明 | 把"没出现的输出"当信号，如 test result 行 |
| 带过滤跑出的数字 | 范围比你以为的窄，工具却完全正确 | 先跑全集再缩小；报数字必须带范围 |
| 时间窗/阈值写错 | 开大会误报，误报被当成成功收走 | 先问"错了会朝哪边错"；用纪元秒避开时区 |
| "这行必须不出现" | 文件读不到也返回真，取证失败算成了证据 | 空也要落文件；读不到判 FAIL |
| 否定式断言常绿 | 那个模式根本不会出现，断言是空的 | 逐个模式确认它至少出现过一次 |
| 带引号转述对方的话 | 引号里可能是自己的引申 | 分清他说的与我想到的；引申要明说是引申 |
| 判据写成一条命令 | 别的执行者用的是另一套工具，够不到它 | 问"每个执行者都有检查点吗"；另留一条不依赖构建工具的兜底 |
| 工具没报错 | 报错是它愿意说的，产物才是它做过的 | 去看产物：`test result:` 行、文件数、`git status` |
| 共享树里"比基线多几条" | 全局计数是所有人在途工作的和，差值不可归属 | 按身份比：那几条落在谁的文件、谁的符号上 |
| 两台机器结论不同 | 差异来自版本控制之外：生成文件、缓存、环境 | `git check-ignore -v` / `ls-files` 那个文件，别去比提交 |
| 验收没过、命中里有遗留文件 | 改 grep 能让它通过，且不留痕迹 | 按身份分两栏交给裁定的人；尺不许动 |
| 一条读着很确定的理由 | 可能是从名字推的，没执行过验证 | 要求一个只有看过才说得出的细节；否定结论先种阳性样本 |
| 「验证过了」 | 可能只跑到 analyze，构建那一步从没通过 | 列出改动到用户眼睛之间的每一步，标出实际跑过哪几步 |
| heredoc 写出来的文本 | 界定符没加引号时反引号里的词被执行掉，退出码仍为零 | 一律 `<<'EOF'`；判据是做不做替换，不是哪些字符危险 |
| 一个成员「差不多能塞进去」 | 归进去会让已写的注释变成假话 | 加成员,不要硬套;注释是断言,名字不是 |
| 「这是纯重构」 | 逐个举例只是找支持,不构成证明 | 先说出唯一能推翻它的情形,再去查那一个 |
| 认真查过、没发现碰撞 | 查的对象可能比真实对象小(少了形态或维度) | 先问它有几种形态、几个维度;一个维度出界才算证完 |
| 「我核过了」 | 可能是沿着对方的路径重算,盲区照单全收 | 先问对方是怎么得出结论的,然后刻意不走那条路 |
| 表里的十六进制带省略号 | 截断处读起来与完整值一样,对方会拿它复算 | 别人要算的数值一位都不省 |
| 「CI 没红」 | 可能是还没跑完,队列里的运行不是结论 | 看状态列是不是 completed;攒一批再推,别让队列变长 |
| `gh run list` 的输出 | fork 里它默认回答上游仓库,列表看着完全正常 | 一律带 `--repo`;对不上的只有 sha |
| 自己那句准确的话 | 被转述时会朝更强、更简洁漂,限定词最先掉 | 把限定写进同一句,别另起一段 |
| 自己报“已接完”的文件 | “接完”是记忆，清单是测量；局部读数自洽，因为它本来就取自局部 | 照单核一遍；只看失败的那一项，等于没核 |
